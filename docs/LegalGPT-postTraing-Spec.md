# LegalGPT 后训练项目 Spec

## 1. 项目背景

### 1.1 项目定位与训练目标

本项目聚焦于**法律咨询（Legal Consultation）**场景，目标是在**不依赖 RAG** 的前提下，提升通用大模型在法律咨询中的推理质量、回答规范性与建议可执行性。

法律咨询并非简单的法条检索或知识问答，而是围绕案件事实展开分析、依据法律规则形成判断、进而给出可执行建议的**结构化推理**过程（借鉴 DISC-LawLLM 的法律三段论思想）。然而，通用大模型虽具备法律知识，却难以自然遵循这一推理范式。DISC-Law-SFT、Lawyer-LLaMA、华律网等数据源在回答风格、推理粒度和法律依据表达方式上差异明显，导致监督信号不一致。

因此，本项目通过数据工程统一监督信号（定义 canonical 格式作为三源对齐目标），再结合 **SFT → DPO → GRPO（后备）** 的完整后训练管线，实现从通用语言模型到专业法律咨询模型的能力迁移。具体方法分工：

- **SFT**：用大量 canonical 格式的重排样本进行监督微调。聚焦教会模型”回答应该怎么展开”：理解用户案情→识别法律关系→展开法律分析→给出规范化建议。解决推理链缺失和回答风格不稳定的问题。
- **DPO（主）/ GRPO（后备）**：通过偏好对或规则奖励，惩罚直接下结论、遗漏用户诉求、编造法律名称等低质量行为，在 SFT 基线上收紧行为边界。

> **学习：** 先弄明白后训练有哪些常见手段：SFT 有哪些训练方式，强化学习或偏好对齐有哪些方法，它们分别适合解决模型输出中的哪些问题。
>
> **思考：** 你的项目可能会出现哪些效果问题？结合法律咨询任务特点分析：模型是否能够准确理解用户描述的案件事实、识别正确的法律关系、围绕事实展开完整分析、给出具体可操作的建议、是否存在法律幻觉或过度推断问题。

### 1.2 任务定义与职责边界

模型的核心职责是作为智能法律咨询助手，帮助用户完成初步法律问题分析、风险提示和解决路径建议——不是替代律师。输入为自然语言的法律咨询问题，输出为规范化法律咨询回答，需包含：对用户情况的理解、涉及的法律关系及依据、基于现有事实的判断、具体可操作的处理建议。

例如，输入：

> 公司拖欠工资三个月，没有签劳动合同，现在要求我离职，我应该怎么办？

模型需识别：存在劳动关系、涉及工资支付和合同问题、用户关注维权方式和补偿；输出需完整覆盖这四个环节。

**模型不负责：** 实时法律法规检索、精确背诵法条编号、替代律师出具正式法律意见、根据未知事实预测案件结果、自动生成诉讼文书。

#### 1.2.1 五类任务场景

> ❓ **思考：** 本节梳理法律咨询模型需要处理的业务场景及判断逻辑，为后续 SFT 样本设计和偏好数据构建提供依据。具体输入输出格式在数据制作阶段统一。

| 类型 | 场景 | 判定逻辑 | 关键决策 |
|------|------|---------|---------|
| 1. 信息充分 | 用户提供完整案件事实 | 诉求明确，足以初步分析 | 输出”事实理解→法律定性→说理→建议”的完整推理链，不跳步 |
| 2. 信息不足 | 关键事实缺失（时间/证据/关系等） | 无法确定基本法律关系 | 不编造缺失事实；基于已有信息有限分析；用”如果…则…””若能够证明…则可能…”等条件化表述，不给绝对结论 |
| 3. 复杂案件 | 同一问题涉及多个法律关系 | 单一结论覆盖不全 | 对不同争议点分别分析，逐一给出对应建议 |
| 4. 法律不确定 | 模型无法确认具体适用规则 | 知识不确定性或需结合本地化因素 | 避免虚构法条编号或绝对化结论，可说明可能的适用方向 |
| 5. 无关/超出能力 | 用户输入与法律无关，或超出模型能力边界（如起草诉讼文书、查询实时法规、需要执业资质才能回答的事项） | 不属于法律咨询范畴，或需要模型不具备的能力 | **礼貌拒答，诚实说明边界**。不使用模棱两可的表达暗示自己能答，不为了显得”有帮助”而编造回答。正确示范：”这是需要执业律师根据具体案情起草的法律文书，我无法代为撰写，但可以帮您分析其中涉及的法律要点。”错误示范：硬给一个不专业的答案 |

> **理解用户法律问题 → 识别法律关系 → 基于事实展开分析 → 提供规范化处理建议。** 类型 5 确保模型具备”知道不该答的时候不答”的边界意识，是 1.3.3 诚实边界在任务层面的落地。
>
> **📝 修订 (2026-07-23):** 原六类场景中的”类型 5：用户要求法律依据”已移除。理由：该场景的行为要求（引用法律名称、不写条文编号）与类型 1 完全一致，canonical 格式本身已覆盖；真实数据中也几乎抽不到以此为独立诉求的样本（两轮 1100 次分类仅 20 条）。六类缩减为五类（原类型 6 顺延为类型 5）。评测矩阵相应从 11×5 调整为 11×4（排除类型 5），配额 10/10/5/5。
>
> **📝 修订 (2026-07-27):** 类型 3（复杂案件）从评测体系中移除。~~原”类型 3：复杂案件”作为独立评测维度已删除。~~ 理由：类型 3 定义”涉及两个以上独立法律关系”——其核心诊断维度 completeness（”模型会不会遗漏”）要求标注者能够识别所有涉及的法律关系并判断回答是否遗漏。非法律专业标注者无法可靠完成这一判断。标注者既无法确认 LLM 预分类是否正确（51 条类型 3 从未经法律专业人士审核），也无法对 completeness 维度打出有意义的分数——标注者的判断上限是”有引用”而非”引用正确”，是”看起来完整”而非”没有遗漏”。这导致类型 3 的 completeness 评测从根本上不可靠。**训练场景定义保留**（模型仍需处理复杂案件，SFT 数据中保留涉及多法律关系的样本），但**评测维度从 3 类缩减为 2 类**（信息充分/信息不足 + 类型 6 拒答）。评测矩阵相应从 11×3 调整为 11×2。原 51 条类型 3 样本重新标注为类型 1，统一使用 LLM-Judge 五维评测。

### 1.3 后训练的诚实边界

本项目 55% 的训练答案由外部 LLM 生成，剩余 45% 也需经 LLM 重写。一个无法回避的问题是：**训练出的模型学到的是法律知识还是生成模型的说话风格？**

> **❓ 思考：** 这个问题需要正面回答——不是否认合成数据的风险，而是诚实地界定后训练能解决什么、不能解决什么。

后训练的定位可以用两个正交维度说清：

| 维度 | 含义 | 谁负责 |
|------|------|--------|
| **形式质量** | 推理链是否完整、格式是否规范、建议是否具体、是否避免了幻觉 | **后训练**（SFT+DPO） |
| **内容正确性** | 法律概念对不对、依据是否恰当、结论是否符合司法实践 | **基座模型**的预训练知识 |

SFT 做的不是”告诉模型哪个结论正确”，而是”告诉模型把你已有的法律知识按这个格式组织输出”——结论来自基座模型的预训练知识，后训练只教表达方式。

**三条防线保证后训练不会让法律知识变差：**

1. **知识保真度回归测试（2.5.2）**：DISC-Law-Eval 客观题 accuracy 下降 = 训练出问题，立即停训排查
2. **后训练在降低而非增加幻觉**：SFT 正例 + DPO 偏好对惩罚，实际上在收紧”编条文编号/猜法律名称/虚构数字”等行为边界
3. **表达了”不知道”的权利**：SFT 中的信息不足正例教会模型”关键事实缺失时指出缺了什么、在什么条件下可能是什么结果”

**最尖锐的问题：如果生成模型的结论是错的，SFT 会学到这个错误吗？**

如果错误是系统性的（如”始终在劳动争议中引《民法典》而非《劳动合同法》”），SFT 确实可能学到偏差。控制机制：(a) 法律名称白名单降低编造概率；(b) 基座预训练知识作为强先验——少量错误样本不会覆盖已有的知识分布；(c) 第二层评测暴露系统性错误引用，倒逼数据修正。

最终诚实的结论：**后训练的上限是”把基座模型已有的法律知识用正确的格式表达出来，同时不编造、不敷衍、不绝对化”。法律正确性的上下限都由基座模型决定——后训练不改写知识本身，只改表达方式。要提升正确性本身，需要 RAG 或律师标注数据。这不是缺陷，而是诚实的职责边界。**

#### 1.3.1 为什么训练模型不输出条文编号

本项目要求模型”引用法律名称但不写具体条文编号”。如果将这个决策简单地解释为”因为不接 RAG 所以不需要条文编号”，在面试中容易被质疑：现在主流法律 AI 都配 RAG，为什么还要花精力训练一个”不提条文”的模型？

这个决策有更基本的技术理由，从三个递进层次论证：

**（1）技术边界：无 RAG = 无法验证。** 这是最基本的事实约束。模型没有检索工具，无法在推理时查证任何一个条文编号是否正确。基座模型预训练时确实可能记住了某些条文编号，但这个记忆不可靠——同一个模型可能对《劳动合同法》相关编号记得很准，对冷门法律的编号完全编造。用户无法区分”模型记住了”和”模型在编”。在无法验证的前提下，输出条文编号就是赌博。

**（2）安全决策：不确定的权威展示比诚实的模糊陈述更有害。** “根据《劳动合同法》的相关规定，你有权主张双倍工资”和”根据《劳动合同法》第82条，你有权主张双倍工资”，对普通用户来说后者的权威感远高于前者。如果第82条是对的，固然好；如果是错的，用户会基于错误信息采取行动。在法律场景下，**错误的权威比没有权威更危险**。宁可让用户知道”模型告诉我应该按《劳动合同法》维权，但具体条文我得自己查”，也不要让用户带着一个错误的条文编号去仲裁。这与人类律师的咨询习惯一致——律师在初步咨询阶段给出的也是”根据《担保法》”，精确条文引用需要对照权威文本后才能给出。模型的行为模式应对标人类律师的咨询习惯，而非考试答题。

**（3）诚实边界本身是可迁移能力。** “不提条文编号”不是机械的行为约束，而是教模型区分”我能验证的”和”我只能推测的”。这个元认知能力在 RAG 场景下直接升级为：检索到的内容 → 可引用编号；记忆中的内容 → 不编造编号。一个经过无 RAG 诚实训练的模型接入 RAG 后，行为会自然演化为”对检索结果引用编号、对记忆内容模糊引用”——比一个未经训练的模型更可信。此外，LoRA 适配器（rank=32，几十 MB）只覆盖不到 1% 的模型参数，基座模型的法律知识未被破坏——后续做 RAG 时卸掉此适配器、换上 RAG 友好的适配器即可，全部训练投入没有浪费。

**（4）无 RAG 场景是整个 RAG 系统的 fallback 态。** 即便是配有 RAG 的管线，当检索不到相关内容或检索结果不相关时，模型退化为无 RAG 状态。此时它的行为模式是什么——诚实地说”根据相关法律规定”，还是凭空编一个条文编号？训练模型在 fallback 态下保持诚实，这本身就是 RAG 管线的一环。

> **面试回应要点**：本项目训练的是”引用规范”和”诚实边界”这两个行为模式，而非”无 RAG 场景下的法律咨询能力”。这些行为模式与是否接入 RAG 正交——RAG 解决”找得到什么信息”，本项目解决”找到/找不到信息时怎么表达”。先在没有工具的情况下培养诚实习惯，再给工具让它做得更好。

### 2.1 基座模型选择

> **❓ 思考：**
> 模型的选型是面试中最常被追问的问题，需要从任务需求、模型能力、训练管线、部署条件等多个维度建立充分的论证链。本节的核心逻辑是：先明确约束（什么能做、什么做不了）→ 再拆解任务对模型的能力要求（需要模型会什么）→ 然后筛选候选池 → 最终通过实验而非纯文字推断来确认选型。
>
> **实验驱动原则：** 选型的最终结论不是写文档就能确定的——几个候选模型在相同数据、相同训练方案下跑完实验矩阵后，哪个表现更好、哪个在我们关注的维度上更适合，才下结论。文档阶段的任务是把候选池收敛到少数几个有理有据的方向，并设计好对比实验框架。

#### 2.1.1 选型目标与约束

基座模型选型受以下几方面约束，这些约束共同决定了候选模型的规模范围、训练方式和选择优先级。

**（1）任务形态：结构化推理输出，而非开放域生成。**

从第 1 章的任务定义出发，本项目训练后的模型需要完成的是法律咨询场景下的结构化推理回答——理解用户事实、识别法律关系、围绕事实展开分析、给出处理建议。输出形态是 300-400 字的规范化咨询回答，包含推理链但不过度展开，不涉及多轮工具调用或实时检索。这一任务形态决定了：
- 模型需要的是**法律概念理解 + 事实推理链生成 + 规范化输出**的能力组合，而非通用知识覆盖度或超长上下文处理能力
- 不需要 Function Calling / Agent / 多模态能力
- 输出空间比开放问答更收敛，但比 JSON 抽取更灵活，属于"有结构但不僵化"的中间形态

**（2）训练管线约束：≤ 7B + LoRA 高效微调，覆盖 SFT → RL 全管线。**

这一约束来自训练预算（autoDL 约 200 元）与完整后训练管线（SFT → DPO/GRPO）的叠加。预算约束的详细分析见 2.3.3（训练算力选择），此处不展开。直接结论是：

- 模型规模控制在 7B 及以下，配合 LoRA 微调（rank 16-64，target_modules 为注意力层 q_proj/v_proj），可训练参数约 0.5%-2%，以在 24GB 显存单卡（如 RTX 4090）上同时容纳基座权重、LoRA 适配器和 RL 阶段的多模型组件
- 更小的模型（如 1.5B-4B）虽然推理链生成质量可能不如 7B，但在法律咨询这个"有结构但不僵化"的任务上，配合精心设计的 SFT 数据和 RL 对齐，可能以更低的训练成本达到可接受的质量——这需要在实验中验证
- 14B 及以上模型即使使用 QLoRA，RL 阶段的显存压力（policy model + reference model）在单张 24GB 卡上也难以稳定运行，且全管线训练时间会超出预算

**（3）中文法律能力优先。**

训练数据以中文法律咨询为核心（DISC-Law-SFT + Lawyer-LLaMA + 华律网），目标场景不需要多语言能力。选型时优先考虑中文预训练语料占比高、中文法律相关评测表现好、中文指令遵循能力强的模型。英文法律能力不作为选型依据。

这一约束同时意味着：候选模型的 tokenizer 需要对中文法律文本有高效的编码效率（中文法律术语不应被过度拆分为 subword），否则会在有限的上下文窗口内损失信息密度。

**（4）指令微调版本优先（Instruct/Chat 变体）。**

候选模型应为经过指令微调的版本，而非基座预训练版本。原因：指令微调版本已经具备基本的对话格式遵循能力和安全对齐，可以直接进入领域 SFT 阶段，不需要额外花费预算做通用指令微调。同时，指令微调版本在法律咨询这种"需要理解用户问题、给出结构化回答"的任务上，起点比裸基座高——它们已经学会了"听到问题→给出有帮助的回答"这一基本行为模式，领域 SFT 只需要在此基础上教会"什么样的回答才是好的法律咨询回答"。

**（5）开源可微调，生态成熟。**

候选模型需要：开源权重（允许商用或研究用途）、LLaMA-Factory / TRL 等主流训练框架明确支持、社区有可参考的 LoRA 微调案例、支持 GGUF 量化部署（为后续可能的本地方案预留）。

#### 2.1.2 任务能力需求分析

结合第 1 章的任务定义与 1.2.1 的五类任务场景，本项目对基座模型的能力要求可以拆为六个维度。这些维度共同定义了"什么样的基座模型更适合做法律咨询 SFT"——它们不是从 benchmark 榜单上照搬的，而是从法律咨询这个具体任务形态中反推出来的。

**一、中文法律概念理解能力。**

法律咨询回答的核心不是法条检索，而是在正确的法律概念框架下展开分析。用户说"老板拖欠工资"——模型需要理解这涉及"劳动报酬""劳动关系""用人单位"等法律概念，而不是将其当成一般的"欠钱不还"来处理。用户说"我想离婚，孩子归谁"——模型需要激活"抚养权""共同财产""过错方"等婚姻家庭法域的概念网络。

这一能力直接决定了领域 SFT 的起点高度：如果基座模型对"工伤""违约责任""诉讼时效"等基础法律概念没有正确的语义理解，SFT 阶段需要先做概念对齐才能进入推理链训练，这会消耗宝贵的训练预算。反之，如果基座模型已经在预训练中建立了较好的中文法律概念分布，SFT 可以跳过概念教学阶段，直接进入"如何用这些概念做推理和回答"的范式训练。

**二、事实提取与案情理解能力。**

法律咨询的输入是用户用自然语言描述的案件经过，其中混杂了事实陈述（"他打了我"）、情绪表达（"我实在受不了了"）、主观判断（"他肯定是故意的"）和不完整信息（"大概是上个月的事"）。模型需要从中提取出对法律关系判断有影响的关键事实，而不是将用户的每一句话等同对待。

具体包括：识别事件的时间顺序和因果关系；区分用户的主观感受和可验证的事实陈述；从口语化表达中提取法律上有意义的信息（如"他让我走"→可能涉及"单方解除劳动关系"）；识别用户描述中的信息缺口（用户只说了结果没说原因、只说了对方的行为没说自己的诉求）。

这一能力对所有五类任务场景都至关重要——无论信息充分还是不足，模型首先需要正确理解"用户说了什么、没说什么"。

**三、结构化推理链生成能力。**

这是本项目与一般法律问答类 SFT 项目的核心区别。我们不是训练模型做"问题→法条→结论"的一步式回答，而是要求模型输出包含"事实理解→法律定性→法律依据+说理→结论建议"的完整推理链。

这要求基座模型具备：多段落连贯生成能力（300-400 字的结构化输出，段落间逻辑递进而非简单罗列）；从具体事实到抽象法律规则的映射（归纳推理）；从法律规则到具体结论的推演（演绎推理）；在推理过程中保持对原始事实的忠实（不为了推理完整而补全用户没说的信息）。

这一能力在大多数基座模型的预训练中并非显式训练目标——通用模型的预训练分布以短问答、百科知识、代码、对话为主，长篇结构化推理的比例较低。因此，无论选哪个基座模型，这一能力主要靠 SFT 阶段训练出来；但基座模型的指令遵循能力和长文本生成质量会直接影响 SFT 达到收敛所需的样本量。

**四、指令遵循与输出格式控制能力。**

法律咨询回答有一组明确的格式约束：引用法律名称用书名号但不写条文编号、不编造精确数据、不做绝对化预测、信息不足时用条件化表述、不使用标签化结构词（"首先/其次/最后"等）。这些约束需要在 SFT 阶段被学习，但基座模型的指令遵循能力决定了学习效率。

指令遵循能力强的模型（通常是在大规模指令微调中训练出来的）能够用更少的 SFT 样本收敛到目标格式；指令遵循弱的模型可能需要更多的 SFT 样本和更长的训练步数，且容易出现格式回退。

**五、幻觉抑制与事实边界意识。**

法律咨询场景对幻觉的容忍度极低——编造一个不存在的条文编号、虚构用户没说过的事实、给出没有依据的确定性结论，都比"承认不确定"的后果更严重。基座模型如果本身有较强的幻觉倾向（如在不确定时倾向于"猜一个"而不是表达不确定），后续 SFT/DPO 需要投入大量样本专门做边界控制。反之，基座模型在指令微调阶段已经被训练出较好的"不知道时就说不知道"的行为模式，领域对齐时只需保持即可。

**六、中文长文本上下文处理能力。**

法律咨询的输入（用户问题）通常较短（50-200 字），单轮问答不需要 128K 超长上下文。但训练时每条样本需容纳：system prompt + 用户问题 + 模型输出（300-400 字）。实际上下文需求在 1K-2K tokens 以内，32K 上下文窗口已经充足。上下文长度在此作为门槛项（满足即可），不作为核心选型差异点。

但需要注意：tokenizer 对中文法律文本的编码效率会影响有效上下文容量。如果 tokenizer 将常见法律术语（如"劳动合同""行政复议""诉讼时效"）拆分为过多的 subword token，实际可用的信息密度就会降低。候选模型对比时应关注中文法律文本的 token 压缩率。

#### 2.1.3 候选模型池

候选池收敛到 Qwen 系列内的三个档位，分别回答不同的问题。

**（1）主力：Qwen2.5-7B-Instruct。**

7B 是当前中文开源社区最成熟的量级——SFT/LoRA/DPO 的社区案例最丰富，LLaMA-Factory 的支持最稳定，训练和部署的工程风险最低。Qwen2.5-7B-Instruct 在中文指令遵循方面经过了充分验证，法律概念理解准确，且 2.5 版本相比更早的 Qwen2 版本在长文本生成和多段落连贯性上有显著提升（官方报告），这两项恰好是 2.1.2 中强调的法律推理链生成所需要的基础能力。它作为主力候选，承担"7B 量级在法律咨询 SFT 上能走多远"的核心验证。

**（2）精简档：Qwen3-4B-Instruct。**

4B 是当前仍能保持可接受中文能力的较小量级。它在候选池中的角色是回答一个问题：比 7B 小近一半的模型，经过相同 SFT 数据训练后，法律推理链的质量能接近 7B 到多少？如果 SFT 后 4B 的推理链完整性和法律依据准确性能达到 7B 的 80% 以上，那更小的部署成本和更快的推理速度就是实际优势；如果差距显著，则确认 7B 是法律咨询场景的最小可行规模。

需要说明的是，Qwen3-4B 默认带有 thinking 模式（`<think>` 推理块）。在本项目的任务中，推理过程应显式出现在回答正文中而非被隐藏在 think 标签里，因此训练和推理时需要关闭 thinking 模式（`enable_thinking=False`），确保模型学习的是"把推理过程写在回答里"而非"在内部思考然后给简短回答"。

**（3）上限档：Qwen3-8B-Instruct。**

8B 比 7B 多约 14% 的参数量。放在候选池中的目的是与 Qwen2.5-7B 对比，回答：对于法律咨询这个任务，更大的参数量（4B→7B→8B）是否带来成比例的推理链质量提升？如果 8B 显著优于 7B，则法律咨询任务可能受益于更大的模型容量；如果两者接近，则说明 7B 已经接近该任务的容量饱和点，选 7B 因为生态更成熟。

**为什么候选池不跨家族对比？**

面试官可能追问："你只比了 Qwen 内部三个档位，怎么知道 Qwen 本身是最适合法律咨询的模型家族？"

这个实验要回答的问题是**规模效应**——给定 200 元预算，7B 量级在法律咨询上是否足够？4B 能不能用？8B 值不值得多花参数成本？Qwen 4B/7B/8B 的组内对比直接回答了这三个问题。跨家族对比（Qwen vs DeepSeek vs InternLM）回答的是另一个问题——"哪个家族的法律中文预训练更好"——这可以通过公开 benchmark 预筛：

- **LexEval**（NeurIPS 2024）：23 任务、14,150 题，评测了 38 个 LLM 的中文法律能力。Qwen2.5-7B 在法律知识维度排名前列，与 DeepSeek-7B 差异在 3% 以内
- **LawBench**（arXiv:2309.16289）：20 任务，含华律网咨询评测子任务。如果候选模型在零样本法律咨询上就有显著差距，选型时可直接筛掉弱势方

公开 benchmark 已经覆盖了跨家族比较的维度。首轮预算（200 元、约 25-33 GPU 小时）花在验证规模效应上——因为规模一旦定错（比如选了 4B 但法律推理链质量不够，或者选了 8B 但和 7B 无差异），修正成本远高于加一个候选模型。跨家族验证在基座选型确认后，用中选模型的 SFT/DPO 权重和另一家族的同等规模模型做单次对比即可——不需要在选型阶段花三倍预算把每个家族的三档都跑一遍。

**不进入候选池的模型：** ChatGLM 系列主力尺寸偏 9B/32B，小尺寸不连续；MiniCPM 的 2B 规模推理链生成能力有限。这些在 2.1.1 的约束下自然排除，不涉及"比 Qwen 好还是差"的主观判断。

#### 2.1.4 对比实验设计与选型决策

**实验矩阵：**

| 模型 | 规模 | 训练方案 | 验证问题 |
|------|------|---------|---------|
| Qwen2.5-7B-Instruct | 7B | LoRA SFT | 7B 量级作为法律咨询基座的上限如何？ |
| Qwen3-4B-Instruct | 4B | LoRA SFT | 更小的模型能否产出可用的法律推理链？ |
| Qwen3-8B-Instruct | 8B | LoRA SFT | 参数从 7B 增到 8B 是否有显著的边际收益？ |

三组统一固定变量：同一训练数据集（约 7,600 条 canonical 格式咨询回答）、同一 LoRA 配置（rank=32，target_modules=q_proj+v_proj）、同一 SFT 超参、同一评测集。

**为什么基座选型只做 SFT 对比，不做 RL 对比？**

这个问题需要正面回答——毕竟本项目最终会跑 DPO，选型时如果只看 SFT 结果，会不会忽略不同基座对 DPO 的响应差异？

核心论点是：**在这个任务中，SFT 阶段就已经能把基座差异拉开到足够做决策的程度，DPO 的增量大概率是等比例的，不会翻盘。**

具体来说：

1. **SFT 是能力构建，DPO 是边界修正。** SFT 负责教会模型"法律咨询回答应该长什么样"——推理链结构、法律概念运用、格式规范。如果模型在 SFT 阶段连基础格式都学不会，DPO 无法通过偏好对把格式从不可用推到可用——DPO 擅长的是在已有能力基础上收紧边界，而不是从零构建能力。

2. **跨基座的 SFT 差异 >> 跨基座的 DPO 差异。** 三个候选模型的核心区别在于预训练中文法律概念分布、指令遵循基础、长文本生成质量——这些差异在 SFT 阶段就会充分暴露。DPO 的增量（比如通过偏好对惩罚进一步减少幻觉、优化建议可执行性）对于同一个基座来说是边际改善，不太可能让一个 SFT 阶段明显落后的模型反超领先者。换句话说，如果 4B 在 SFT 后推理链完整性显著低于 7B，DPO 不可能把它拉到 7B 的水平——因为 DPO 并不教模型新的法律概念或更强的推理链生成能力，它只是在已有输出的基础上收紧边界。

3. **预算有限，实验设计需要功利。** 三组 SFT 总计约 8-10 GPU 小时。如果把 DPO 也纳入基座对比，三组 × (SFT + DPO) 的训练时间会大幅增加——而这多出来的预算，花在验证一个大概率不翻盘的假设上，不如省下来投入到最终中选模型的 DPO 调优上。

因此选型决策逻辑是：三组 SFT 跑完后，比较评测指标——

- 如果 4B 达到 7B 的 80% 以上水平 → 选 4B（成本优势明显）
- 如果 7B 和 8B 差距 < 5% → 选 Qwen2.5-7B（生态更成熟，权重更小，成本更低）
- 如果 8B 显著优于 7B（>10%） → 选 Qwen3-8B（法律咨询任务受益于更大容量）
- **中选模型进入完整 DPO 管线（GRPO 后备），其余模型不再投入**

#### 2.1.5 选型总结

基座模型选型的核心逻辑概括为：

- **约束层面**：≤ 8B + LoRA，中文法律能力优先，指令微调版本，覆盖 SFT + RL 全管线但选型仅需 SFT 对比
- **能力层面**：法律概念理解是起点，推理链生成和指令遵循决定 SFT 收敛效率，幻觉抑制决定回答可靠性
- **候选层面**：Qwen 系列三档（4B/7B/8B），分别回答"最小可行规模""7B 上限""规模边际收益"三个问题
- **决策层面**：三组 SFT 对比决定基座，中选模型进 DPO（GRPO 后备）；SFT 差异足够支撑决策，DPO 大概率等比例增量，不会翻盘

> **📝 最终结果（2026-08 训练收尾）：** 实际只跑 Qwen2.5-7B-Instruct，未做三模型对比——审慎度/拒答的短板是 SFT 方法瓶颈（见 Phase 5 设计），换基座不能解决。

### 2.2 后训练方法选择

后训练不是"为了训而训"。本节先梳理法律咨询模型需要解决的全部痛点，再分析 SFT 和 RL 分别适合解决其中哪些问题，最后给出两阶段后训练的组合方案。

#### 2.2.1 项目痛点

以下痛点中，P1、P2、P4、P5、P6 来自 Phase 1 对 DISC（2,696 条保留）和 zixun（348 条保留）的数据统计，P3 来自任务场景分析——本项目无 RAG、法律名称全靠模型记忆，SFT 教会模型"引用法律名称"的同时也制造了幻觉风险。

| 编号 | 痛点 | 具体表现 | 证据 | 典型 case |
|------|------|---------|------|----------|
| P1 | 推理链缺失 | 一步到位式回答，缺少从事实到法律判断的推理展开过程 | DISC **41.7%** 篇幅<200字，**88.2%** 推理信号≤1 | DISC："根据《城乡规划法》，农田建棚属于违法建筑。" — 法律→结论，中间无推演 |
| P2 | 格式不规范 | 条文编号（"第1079条"）、标签化结构词（"首先/其次/最后"） | DISC 编号 0.6%（Phase 1 清洗残留）；zixun **标签词 31.3%** | zixun："首先，根据《民法典》…进一步分析…在实际操作中…值得注意的是…" — 模板化严重 |
| P3 | 法律依据幻觉 | 编造不存在的法律名称、或者在与该法律无关的场景中强行引用 | **任务驱动论证**：本项目无 RAG，法律名称完全依赖模型记忆；SFT 教会模型"回答需要引用法律"的行为模式，但格式约束本身不解决"什么场景该引用什么法"的判断——模型在不熟悉的领域可能从训练数据中"借"一个看起来相关的法律名称来用 | DISC 数据中存在"中华人民共和国林业法"（无此单行法），Phase 1 已用法律名称白名单约束生成 prompt |
| P4 | 法律概念误用 | 将法律关系归入错误领域（工伤→侵权、劳动合同→合同纠纷） | 华律网"合同纠纷"标签中 36% 经 LLM 重分类后修正为劳动/房产/婚姻家庭等其他类别 | "签合同第二天工伤"被标为合同纠纷；"协议离婚需要多久"被标为合同纠纷 |
| P5 | 建议空泛 | 以"建议咨询律师""以实际情况为准"收尾，不给具体操作步骤 | DISC 7.2%；zixun **32.4%** | zixun："具体情况需要根据法律和事实进行综合判断。" — 读完不知道该做什么 |
| P6 | 过度确定性 | 信息不足时仍给出绝对化结论，使用"一定/必然/肯定能" | DISC 5.6%；zixun **21.1%** | zixun："女方肯定能获得抚养权，法院必然判给母亲。" — 实际需综合多种因素 |

#### 2.2.2 SFT 方案分析

SFT 用"用户问题 + 规范回答"的精标样本训练模型。它是整个后训练管线的基线——P1-P6 全部需要 SFT 先打底，区别只在于哪些痛点 SFT 已经基本够用、哪些还需要后续 RL 进一步收紧。

**（1）参数更新方式**

| 方案 | 做法 | 优点 | 缺点 | 本项目契合度 |
|------|------|------|------|------------|
| LoRA | 冻结主干，仅训练低秩旁路矩阵 | 显存省、训练快、适配器可插拔便于多模型对比 | 极端收敛弱于全参 | **高**：三组基座对比需要低成本可复现的实验框架 |
| QLoRA | 4bit 量化基座 + LoRA | 显存最省，单卡可训更大模型 | 训练速度略慢 | 中：7B 模型 24GB 卡上 LoRA 已够用，QLoRA 仅在需要更大 batch size 时使用 |
| 全参数微调 | 更新全部权重 | 拟合最强 | 显存高、多实验切换不灵活、LoRA 合并后才能进 RL | 低：预算不支持全参 + RL 管线 |

**结论**：SFT 阶段采用 **LoRA**，rank 32，target_modules=q_proj+v_proj。如果三组基座对比中显存紧张，对 8B 模型降级为 QLoRA。

**（2）SFT 能解决什么、解决不了什么**

SFT 擅长教会模型"正确答案长什么样"。对于格式约束明确、正确模式可枚举的问题（P1 推理链结构、P2 格式规范），SFT 通过足够多的正例可以直接收敛。对于需要判断"在什么情况下不该做什么"的边界性问题（P3 法律依据幻觉、P5 建议空泛、P6 过度确定性），SFT 只看到正例、没看到"为什么某个错误答案不行"，在边界上容易漂移。

具体来说：SFT 可以教会模型"信息不足时应该说'如果您能提供XX情况，可以进一步判断'"——但如果训练集中大部分样本都是信息充足的，这种边界样本被淹没，模型在实际推理时仍然倾向于模仿高频的"直接给结论"模式。这就是 SFT 的天然短板——它通过模仿来学习，而边界控制需要对比来学习。

#### 2.2.3 强化学习 / 偏好对齐方案分析

RL 阶段的任务是在 SFT 基线上做边界收紧：让模型在"该不该给确定结论""该不该编法律名称""该不该用套话收尾"这些决策点上更自律。以下从任务匹配度、效果上限、性能与稳定性三个维度对候选方案进行对比。

**（1）候选方案概览**

| 方案 | 做法 | 任务匹配度 | 效果上限 | 性能与稳定性 |
|------|------|-----------|---------|------------|
| DPO | 用 (chosen, rejected) 偏好对直接优化对比损失，离线训练 | 见下文 | 见下文 | 离线训练、无在线采样，仅需 policy + reference 两份权重 |
| ORPO | 在 SFT loss 上叠加 odds-ratio 偏好损失，无需 reference model，单步完成 SFT+对齐 | 中高：适合"SFT 已大敛但边界不稳"的场景 | 中等：对比信号弱于 DPO（无显式 chosen/rejected 对），但避免了 SFT→DPO 两阶段的灾难性遗忘风险 | 显存最优（仅需一份权重 + LoRA），训练最简（单步），在 MedicalGPT 等项目中已验证 |
| GRPO | 组内相对优势估计，免价值网络；用可验证奖励函数引导在线策略优化 | 见下文 | 见下文 | 需在线采样多份候选、训练不如 DPO 稳定、无需独立奖励模型 |
| PPO | 训练独立奖励模型 + 在线策略优化 | 低 | 高但不可靠 | 四模型协同、训练不稳、显存大 |

PPO 直接排除。以下重点分析 DPO（首选）、ORPO（候选）与 GRPO（后备）。

**（2）任务匹配度（最关键维度）**

选 RL 方法的本质问题是：**SFT 之后的残余错误，是"不知道该选哪个更好"，还是"知道但控制不住"？**

本项目六个痛点中，P2/P3/P5/P6 的共性在于：正确答案和错误答案之间的边界是**已知且可枚举的**。好的回答不写条文编号、不编法律名称、不给套话收尾、不用绝对化表述——这些"不做什么"的规则可以被精确地翻译成程序化的判断（正则检测、白名单匹配）。差的回答是可以被确定性识别的。

DPO 与这种任务形态天然对齐。DPO 的核心机制是"这个回答比那个好"——chosen/rejected 对比损失直接拉大正确行为和错误行为在 logit 空间上的距离。对于 P2/P3/P5/P6，chosen/rejected 的构造极其廉价：拿一条 SFT 输出，程序化注入一个错误（插入 `第X条`、把具体建议替换为"建议咨询律师"、加入"肯定能"）→ 这就是 rejected。每个 chosen 可以配多个 rejected，每条 rejected 覆盖一种错误模式。DPO 要做的就是让模型学会"永远不要选那个"。

GRPO 的核心机制是"探索更好的解"——在线采样多条候选，用奖励函数给每条打分，用组内相对优势更新策略，鼓励模型往高分区探索。这在数学推理（一个定理可能有多种证法）、代码生成（一个需求可能有多种实现）等需要**探索输出空间**的任务上是有意义的。但法律咨询场景中，一次回答是否更好，主要不由"找到了更优的表达方式"决定，而由"是否犯了已知的格式/依据/建议错误"决定——而这些错误在 SFT 输出中已经是可检测的，不需要在线采样去"发现"。输出空间的探索价值在这里极其有限。

因此，从任务匹配度判断：**DPO 与"边界纠错"的任务形态高度对齐；GRPO 的探索能力在输出空间小、错误可枚举的本任务中几乎没有用武之地。** 这不是"DPO 更简单所以选它"，而是任务本身的形态决定了 DPO 的对比学习比 GRPO 的探索优化更直接有效。

**（3）效果上限**

DPO 的效果上限受偏好对质量和覆盖度约束。对于 P2/P5/P6 这些可规则检测的二元约束，偏好对质量不是瓶颈——规则可以高置信度地判断对错。P3（法律依据幻觉）中"白名单外的法律名称"同样可规则检测，"法律正确但场景不适用"的边缘案例则需要 LLM-Judge 辅助判断偏好对质量。P1（推理链质量）和 P4（法律概念准确）是软维度，不能由规则直接判定——但它们的主要训练手段是 SFT 阶段的 canonical 格式正例，RL 阶段对它们的边际改善有限。

关键问题是：**DPO 能否同时处理多个正交约束？** 答案是：通过多轮 DPO 和多 reject 配对策略可以。第一轮 DPO 的偏好对目标 P2（格式），第二轮目标 P5+P6（建议+确定性），第三轮目标 P3（依据幻觉）——每轮只改偏好对构造策略，不改训练流程。与 GRPO 的"所有奖励函数加权一次性优化"相比，DPO 的分轮策略虽然更慢，但每轮的目标更清晰、训练更可控，且可以在轮次间评估单项约束的改善效果。

因此从效果上限判断：**对于本任务的六个痛点，DPO 通过分轮偏好对策略可以达到与 GRPO 相近的效果覆盖；GRPO 理论上限更高（多约束联合优化的梯度信号更丰富），但这一优势在本任务的输出空间内难以兑现为实际的回答质量差异。** 需要注意的是，这是基于任务分析的理论判断——最终需要在实验中通过 DPO vs GRPO 的消融对比来验证。

**（4）性能与稳定性**

DPO 是离线训练：偏好对提前构造好，训练时只需加载 policy 和 reference 两份 LoRA 权重（显存约为 SFT 的 2 倍，24GB 单卡可承载），不需要在线采样和奖励计算。训练过程与 SFT 类似——稳定的 loss 下降、可复现的结果、单次 run 即可收敛。

GRPO 需要在线采样：每步从当前策略生成 4-8 条候选，在 CPU 上运行规则奖励（正则/白名单）+ 可选的 LLM-Judge 调用，计算组内相对优势后更新策略。虽然免去了独立奖励模型，但训练过程本身不稳定——策略更新后输出分布可能剧烈漂移，奖励信号的方差远大于离线偏好对。首轮实验本身已有三组基座对比需要管理，加上 GRPO 的训练不稳定性，调试成本会成倍增加。

因此从性能与稳定性判断：**DPO 以离线、稳定的训练方式更适合三组候选模型的 RL 阶段对比实验——每组只需要构造偏好对、启动训练、等结果，不需要担心训练不收敛或采样质量波动。**

**（5）GRPO 的角色：后备而非首选**

以上论证并非否定 GRPO 的价值，而是明确它的适用条件：当且仅当 DPO 在某个痛点上遇到效果瓶颈——例如经过多轮 DPO 后 P3（法律依据幻觉）的残余错误率仍然偏高，且怀疑是偏好对质量不足（LLM-Judge 对边缘案例的判断不够准确）而非任务本身不可解决时——GRPO 才作为高成本的二次尝试介入。此时 GRPO 的组内相对优势机制可以对 LLM-Judge 的连续打分信号做出更细腻的响应。但这是"DPO 压不动时的后手"，不是"更强的替代品"。

**（6）GRPO + JEC-QA 法律推理增强：一个独立的探索方向**

以上论证中 GRPO 对开放咨询生成效果有限的核心原因是：咨询回答没有标准答案，奖励信号只能来自规则检测（稀疏、二元）。但 S2K（EMNLP 2025）和 DRG-Sapphire（NeurIPS 2025）的成功实践揭示了一条不同的路径：**用有标准答案的法律数据集做 GRPO，增强模型的通用法律推理能力，再通过 SFT 把推理能力锚定到咨询场景。** 这不是"用 GRPO 替代 DPO"，而是"用 GRPO 做 DPO 做不到的事"——提升基座的法律推理正确性本身。

> **❓ 思考：** DPO 解决的是"格式对不对""边界守不守"，但解决不了"这个法律结论本身对不对"——后者来自基座模型的预训练知识。JEC-QA GRPO 提供了在 200 元预算内直接干预推理正确性的可能。

**（6a）为什么是 JEC-QA。**

JEC-QA 是中国司法考试选择题数据集，26365 道单选题和多选题，每题有 A/B/C/D 四个选项和标准答案。它的核心价值在于：

- **奖励完全确定**：选对 +1，选错 -1。不需要 LLM-Judge、不需要 embedding 模型、不需要人工标注
- **覆盖全法律领域**：刑法、民法、行政法、商法等 15 个法律主题
- **要求复杂推理**：66% 的案例分析题需要多跳推理，远超简单的概念记忆
- **有学术先例**：S2K（EMNLP 2025）在 JEC-QA 上用 GRPO 取得优于 RAG 和标准 SFT 的表现；DRG-Sapphire（NeurIPS 2025）在医疗编码上用同样的"规则奖励 + 选择题格式"验证了 GRPO 对领域推理的增强效果

**（6b）核心矛盾：标签格式 vs 咨询风格。**

GRPO 训练需要 `<answer>B</answer>` 这样的结构化标签以便规则解析正确性，但咨询场景需要自然段落输出。这不是本项目特有的问题——R1 本身也遇到了同样的矛盾（纯 RL 输出推理链有语言混杂和可读性问题）。

R1 和 MedicalGPT 的实践共同验证了同一个结论：**SFT 阶段学到的是"知识+推理能力"，GRPO 阶段学到的是"按标签格式输出推理过程"——两者不在同一层。标签只是输出格式的 wrapper，模型在几个 step 内就能学会新格式，不会冲掉 SFT 阶段注入的推理本身。** 格式奖励 + 正确性奖励的共同作用，会让模型快速收敛到"正确推理 + 正确标签"的联合分布上。

**（6c）三段式方案：SFT → GRPO → 收官 SFT。**

借鉴 R1 的"冷启动 SFT → RL → 后 RL SFT"流程，本项目可以设计为三段式训练：

```
阶段 A：SFT（法律咨询风格建立）
  ~7600 条 canonical 格式咨询回答（不带标签）
  → 模型学会"用自然语言做法律咨询"的表达方式和推理结构

阶段 B：GRPO on JEC-QA（推理正确性强化）
  JEC-QA 选择题 + <think>/<answer> 标签 + 确定性奖励（选对+1/选错-1）
  每步 4-8 个 completion 做组内相对优势估计
  → 模型内部的法律推理能力增强，但输出格式带标签

阶段 C：收官 SFT（风格恢复）
  300-500 条高质量咨询回答（GPT-4o 生成 + 人工过一遍）
  → 模型保留 GRPO 的推理增益，恢复自然语言咨询风格
```

**（6d）为什么阶段 C 只需要 300-500 条。**

阶段 C 的目标不是注入新知识，只是"换回自然语言风格"。格式迁移比知识注入快得多——R1 在后 RL SFT 阶段用极少样本就完成了标签剥离。同时，阶段 C 不能用阶段 A 同一批 LLM 生成的数据——那等于"用同一批可能有问题的数据重新修正自己"。需要独立于阶段 A 的高质量样本：GPT-4o 生成质量高于阶段 A 使用的 DeepSeek（¥10-15），且人工逐条过一遍。300-500 条是一个人可以完成的量。

**（6e）为什么没有改写 JEC-QA 为咨询场景。**

一个自然的想法是将 JEC-QA 选择题改写为咨询场景的 prompt（"用户问：未签合同要赔多少？请分析法律依据并给出结论"），保持规则奖励（关键词命中"二倍工资"即 +1）。这一方案在动机上是合理的——减少标签风格的跨度——但在工程上不可行，因为：

- 改写后奖励从"精确匹配 B"变成"关键词命中二倍工资"，引入模糊性：模型输出"双倍工资"（同义不匹配）→ 0 分假阴性；模型输出"根据第82条，有时可以主张二倍工资但本案不适用"（提到但不是答案）→ +1 假阳性
- 每个知识点需要维护同义词表 + 排除规则，两万道题不可能人工维护
- 奖励函数的可靠性崩塌后，GRPO 的梯度信号变成噪声，训练不可能收敛

因此不改写 JEC-QA，接受 `<think>/<answer>` 标签格式作为 GRPO 阶段的"脚手架"——训完后由阶段 C 拆掉。R1 验证了这个模式可行。

**（6f）当前定位与实施前提。**

此方案目前处于"有论文支撑的探索方向"阶段，不替代 DPO 作为首选 RL 方案。要在本项目实施需满足：

- JEC-QA 数据集许可确认（公开学术用途预期可行）
- 阶段 A SFT 完成且评测基线达标（SFT 不充分 = GRPO 零起点，DRG-Sapphire 已证明）
- 阶段 C 的 300-500 条高质量数据必须由 GPT-4o 生成 + 人工逐条审核
- 预算需覆盖 GRPO 在线采样的额外 GPU 时数（估计 8-10h，约 ¥16-20）

> **📝 修订 (2026-07-24):** 以上思考来自对 S2K（EMNLP 2025）、DRG-Sapphire（NeurIPS 2025）和 R1 训练流程的调研。核心发现：有标准答案的数据集（如 JEC-QA）可以绕过 LLM-Judge 瓶颈做 GRPO；GRPO 增推理能力 + DPO 收紧边界 = 互补而非替代；标签格式冲突已被 R1 的冷启动 SFT → RL → 后 RL SFT 三段式验证解决。此内容不作为当前首选方案，作为"已完成技术调研、有实施路径的探索方向"保留。

**（7）ORPO 与 OPD：两个值得关注的候选方案**

来自 MedicalGPT 的工程实践，两个方案在本项目中虽不作为首轮首选，但具备特定场景下的独特优势：

**ORPO（比值比偏好优化）。** 核心价值是省显存——在 SFT loss 上叠加 odds-ratio 偏好损失，无需 reference model，单步完成 SFT+对齐。对预算紧张的场景（单卡 24GB），ORPO 意味着 RL 阶段的显存从"两份 7B 权重"降到"一份 7B 权重"——这是实打实的 6-8GB 释放。代价是对比信号弱于 DPO（无显式 chosen/rejected 对），且 ORPO 的优化目标和 SFT loss 耦合，调参自由度低于 SFT→DPO 分离的两阶段方案。适用场景：如果 DPO 在 24GB 上显存紧张，或训练时间超出预算，退而用 ORPO 作为 SFT+对齐的合并方案。

**OPD（On-Policy Distillation）。** 核心价值是 teacher 指导 student 在 student 自己的 rollout 上改进——在本项目中特别有价值，因为训练数据本身已经是强模型生成的（4,404 条 GPT-4o 答案 + 3,044 条 LLM 重写答案），本质上已经在做隐式蒸馏。如果后续评测发现 SFT 模型在法律概念准确性（P4）上有系统性问题——即模型学到了 teacher 的风格但没有学到法律判断质量——OPD 可以作为补救方案：不需要重新构造数据，直接让 teacher 对 student 的实际输出打分和修正，针对性纠偏。代价是需要 teacher 模型在训练时在线推理，增加 GPU 时数。不作为首轮方案，但针对"合成数据的法律质量"这个已知风险点预留。

#### 2.2.4 结论：两阶段后训练组合

**采用 SFT（LoRA）打底 + DPO（程序化偏好对）对齐的两阶段方案。GRPO 作为 DPO 效果不足时的后备增强。**

1. **阶段一 SFT（LoRA，response-only loss）**：用约 8,000 条 canonical 格式法律咨询回答，教会模型正确的推理链结构、回答范式和基本法律概念应用。对应里程碑 M1。
2. **阶段二 DPO（LoRA，分轮偏好对策略）**：在 SFT 权重上，分轮构造偏好对——每轮针对 1-2 个痛点（P2 格式→ P5+P6 建议/确定性→ P3 依据幻觉），程序化注入错误生成 rejected。分轮的好处是每轮目标单一、效果可逐轮评估、方便定位瓶颈。若某轮收敛不理想，可针对该痛点追加偏好对或调整构造策略。对应里程碑 M2。
3. **后备增强**：若 DPO 在某个痛点上遇到效果瓶颈（多轮后残余错误率仍偏高），启用 GRPO + LLM-Judge 连续打分作为针对性增强。GRPO 不覆盖全量痛点，只聚焦 DPO 未压住的单一维度。

**痛点 × 训练方法对齐表**

| 痛点 | SFT | DPO | 说明 |
|------|-----|-----|------|
| P1 推理链缺失 | ✅ 主 | ◻ 辅 | SFT 通过 canonical 格式正例教会推理链结构；DPO 用 DISC 原始回答作为 rejected 辅助收紧 |
| P2 格式不规范 | ✅ 打底 | ✅ 主 | SFT 教正确格式，DPO 偏好对惩罚条文编号和标签化结构词 |
| P3 法律依据幻觉 | ✅ 打底 | ✅ 主 | SFT 教"引用法律名但不写编号"，DPO 偏好对区分正确引用与编造引用 |
| P4 法律概念误用 | ✅ 主 | ◻ 辅 | 主要由 SFT 正例覆盖；DPO 可在易混淆法域（劳动/合同）构造对比偏好对 |
| P5 建议空泛 | ✅ 打底 | ✅ 主 | SFT 教"给具体建议"，DPO 偏好对区分具体建议与套话收尾 |
| P6 过度确定性 | ✅ 打底 | ✅ 主 | SFT 教"信息不足时用条件化表述"，DPO 偏好对区分确定性措辞与条件化措辞 |

> 图例：✅ 主要手段 / ◻ 辅助手段。
>
> 一句话结论：**SFT 解决"答案应该长什么样"，DPO 解决"答案不应该有什么"。GRPO 是 DPO 压不动时的后手，不是替代品。** 两阶段分工对齐 P1-P6。

#### 2.2.5 消融实验计划

SFT 和 DPO 各自宣称解决的问题不同（见 2.2.4 对齐表），但只有消融实验能分离两个阶段的真实贡献——面试官追问"你怎么知道 DPO 真的有用"时，需要消融数据而非文字论证。设计两组消融实验：

**（1）Base → SFT 消融。** 对比基座模型 zero-shot 输出与 SFT 后输出，验证 SFT 在 P1（推理链缺失）和格式规范化上的实际增益。这是 SFT 阶段的核心宣称——如果消融结果显示 SFT 后的推理链完整度没有显著提升，说明 canonical 格式的 SFT 数据构造或 prompt 设计有问题。

**（2）SFT → SFT+DPO 消融。** 在中选模型上，对比 SFT-only 权重与 SFT+DPO 权重的评测指标。验证 DPO 对 P2（格式不规范）、P3（法律依据幻觉）、P5（建议空泛）、P6（过度确定性）的实际收紧效果。关键指标：条文编号产出率、绝对化表述比例、拒答准确率——这些规则指标可以直接量化 DPO 的边际贡献。

**消融实验的约束：** 两组消融共用同一评测集（2.5.5 冻结版本），训练数据规模相同（约 7,600 条 SFT 样本），仅控制"是否经过 DPO 阶段"这一个变量。loRA 超参保持不变。不做 DPO-only（跳过 SFT 直接 DPO）——这是无意义的消融，因为 DPO 的参考模型是 SFT 权重，DPO 本身不构建新能力。

### 2.3 训练框架选择

承接 2.2（SFT+DPO，均以 LoRA 实现）与 2.1.4（Qwen 三档实验矩阵），本节确定用什么框架跑训练。核心问题是：需求落在标准流程内就让框架代劳，需要改训练逻辑时才自己写代码。

#### 2.3.1 候选方案

| 维度 | LLaMA-Factory | TRL + PEFT |
|------|-------------|-----------|
| SFT（LoRA） | ✅ YAML 配置即用，`train_on_prompt=False` 默认仅对回复段计损 | ✅ `SFTTrainer` + PEFT，需手动配 completion-only collator |
| DPO（LoRA） | ✅ 内置，支持 LoRA | ✅ `DPOTrainer`，需手动组参考模型 |
| Qwen 系列模板 | ✅ 换 `template` 即可 | ⚠️ 需自行处理 chat template 和 special token |
| LoRA 合并导出 | ✅ `export` 一条命令 | ⚠️ 自写 merge 脚本 |
| 多模型实验矩阵 | ✅ YAML + CLI 循环，换 `model_name_or_path` 即可 | ✅ Python 脚本读配置循环 |
| GRPO（后备） | ❌ 不内置（作者拆到独立项目 EasyR1） | ✅ `GRPOTrainer` 原生支持自写奖励函数 |
| 写训练代码 | 不写，只写 YAML 配置 | 需写 Python |

两者底层共享 transformers / peft / trl，不是平级竞品，而是封装程度不同。LLaMA-Factory 把 SFT/LoRA/DPO 的样板代码做成了配置项，TRL 则提供 trainer 骨架让你自己填细节。

#### 2.3.2 选型结论：LLaMA-Factory 主线，TRL 作为 GRPO 逃生舱

**SFT + DPO 阶段用 LLaMA-Factory。** 两个阶段的训练内容全是标准能力——LoRA SFT、response-only loss、DPO、Qwen 系列模板、合并导出——没有一项需要改训练逻辑。LLaMA-Factory 把它们封装为"配置即用"：一条 YAML 声明模型、数据、方法和超参，`llamafactory-cli train` 一键启动。对三组基座 × 两阶段 = 六次训练的矩阵来说，YAML + CLI 循环跑完，比每次手写 Python 训练脚本更可控、更不易出错。

**GRPO 后备阶段用 TRL。** 这是"跌出标准流程"的触发条件：LLaMA-Factory 不内置 GRPO（其 trainer 仅 `rm/ppo/dpo/kto`），而 TRL 的 `GRPOTrainer` 原生支持自写奖励函数——正是 2.2.4 中 GRPO 后备方案所需的能力。但 GRPO 是 DPO 压不动时才触发的后手，不进入首轮。到时候再下沉到 TRL 写奖励函数，SFT 权重和概念是通的，迁移成本低。

**为什么不选 veRL？** veRL（字节跳动开源的 RL 训练框架）同样支持 GRPO，且在大规模分布式 RL 训练上有明显优势。但它的设计重心不在单卡小规模场景——veRL 的核心价值在于 Ray 分布式调度、多 GPU 并行采样和高吞吐训练流水线，面向的是 70B+ 模型、多卡集群的大规模 RL 训练。本项目单卡 4090 + 7B LoRA + 短回答（300-400 字）的负载特征，完全无法触达 veRL 的适用区间——它的优势（分布式）我们不需要，它的代价（独立部署、额外调度层、配置复杂度）我们照单全收。TRL 作为与当前 LLaMA-Factory/transformers/PEFT 同栈的轻量 RL 库，`pip install` 即可用，API 与现有训练流程一致，更适合本项目"单卡、一次性的个人实验"的定位。若后续扩展到多卡或更大规模模型，veRL 重新成为候选。

> 一句话：**标准需求（SFT/DPO/LoRA）→ LLaMA-Factory 配置驱动、不写训练代码；定制需求（GRPO + 自写奖励函数）→ TRL 写奖励函数。veRL 在单卡小规模场景下优势无法兑现，暂不引入。**

#### 2.3.3 训练算力选择

训练框架（2.3.1-2.3.2）决定"谁帮你写训练流程"，算力决定"这套流程在哪台机器上算"。框架对底层 GPU 无感知——同一套数据 + YAML 搬到任何一台 Linux + GPU 机器上，`llamafactory-cli train` 的跑法完全一样。

**（1）为什么不是本地？**

本地笔记本的 GPU 显存不足以稳定运行 7B 模型的 LoRA SFT（需约 12-14GB），更无法承载 DPO 阶段的双模型（policy + reference）。排除自有硬件，训练在远程 GPU 机器上完成。

**（2）本项目的负载特征**

| 特征 | 对算力的含义 |
|------|------------|
| 个人实验项目 | 不需要高可用、不需要常驻，**用完即关** |
| 只跑 7B（未做三模型对比，见 2.1.5） | 单卡 24GB 即可，**不需要多卡并行** |
| LoRA 小模型微调 | 显存需求低 |
| 单次训练时长短（分钟~小时级） | 单卡顺跑即可 |

#### 2.3.4 训练超参方案

以下超参基于 Qwen 官方 LoRA 微调建议、LLaMA-Factory 默认配置和法律咨询任务特点（短文本、结构化输出、中等数据量）综合确定。首轮按此配置运行，消融实验中可根据实际情况调整。

**SFT 超参：**

| 参数 | 值 | 决策依据 |
|------|-----|---------|
| Learning rate | **2e-4** | LoRA 微调 7B 模型的常用起点；Qwen2.5 官方建议 1e-4~5e-4，法律咨询结构化程度较高、收敛相对容易，取中间偏保守值 |
| Batch size (effective) | **32**（4 per device × 8 accumulation） | RTX 4090 24GB 单卡，7B + LoRA 在 1,536 token 序列下 per-device batch 约 4-6。~7,500 条数据，batch=32 时每 epoch 约 235 步，2-3 epoch 合计 ~700 步 |
| Epochs | **2-3** | 领域 SFT 通常 1-3 epoch 收敛；合成数据占比高（55%），过多 epoch 有拟合合成数据分布的风险。先跑 2 epoch 看验证 loss——若仍下降则追加第 3 轮 |
| LR schedule | **cosine** + 3% warmup | 标准做法；warmup 避免训练初期梯度震荡 |
| Max sequence length | **1,536** | 输入（instruction ~300 tokens + 用户问题 ~150 tokens）+ 输出（~350 tokens），1,536 足以容纳且有安全余量 |
| LoRA config | rank=**32**, alpha=**64**, dropout=**0.05**, target_modules=**q_proj+v_proj** | rank 32 是中等复杂度任务（法律推理链）的平衡点；alpha=2×rank 为标准配比；0.05 dropout 防过拟合 |

**DPO 超参：**

| 参数 | 值 | 决策依据 |
|------|-----|---------|
| Learning rate | **5e-5** | DPO 通常在 SFT 基础上下调 LR——偏好对训练不需要大幅调整权重，只需拉大 chosen/rejected 间隔。参考文档同场景使用 5e-5，LLaMA-Factory DPO 默认亦为此值 |
| Beta (β) | **0.5**（消融后选定） | β 控制 DPO 偏离 SFT 权重的程度。领域 DPO 通常取 0.1-0.5：太低（<0.1）过度优化偏好对、可能损伤 SFT 已收敛的格式能力；太高（>0.5）纠偏乏力。实测消融 {0.1, 0.3, 0.5} 中 0.5 是唯一全维度不退化且有增益的值 |
| Epochs | **1** | DPO 偏好对信号密度高，通常 1 epoch 足够收敛；多轮 DPO 的实现方式是通过追加不同痛点的偏好对（2.4.6），而非在同一批数据上跑多 epoch |
| 其余 | 同 SFT | batch=32, max_len=1,536, LoRA rank=32 |

**调参优先级：** 若首轮效果不佳，优先调 DPO β（对行为边界影响最大），其次调 SFT LR（影响收敛质量），最后调 LoRA rank（影响模型容量）。Bach size 和 max length 原则上不调——前者受限于硬件，后者已对任务留足余量。所有调参结论需在评测集上验证，单靠训练 loss 不能判断法律咨询回答质量的优劣。

#### 2.3.5 训练监控与失败预案

训练过程中的监控指标和异常判定，确保问题能被及时发现而非训完才发现。

**（1）SFT 阶段监控。**

| 监控项 | 正常信号 | 异常信号 | 处理 |
|--------|---------|---------|------|
| Train loss | 平稳下降，2 epoch 内趋于平缓 | 不降或剧烈震荡 | 检查数据格式、LR 是否过高、是否存在脏数据导致 loss spike |
| Eval loss（验证集 10%） | 与 train loss 同趋势下降，差距不扩大 | eval loss 上升而 train loss 下降（过拟合） | 提前停止，减少 epoch 或增大 LoRA dropout；若 1 epoch 即过拟合，检查数据多样性——可能合成数据过于同质化 |
| 生成样本抽查（每 200 步） | 推理链结构完整、格式规范、不编造 | 推理链退化（回到简短结论）、出现条文编号或标签词 | 检查 SFT 数据中 canonical 格式样本的占比和一致性；可能是某些类别的原始回答在重写时未正确对齐 |

**（2）DPO 阶段监控。**

| 监控项 | 正常信号 | 异常信号 | 处理 |
|--------|---------|---------|------|
| DPO loss | 平稳下降 | 不降（β 过大，约束过强） | 降低 β 至 0.1 重试 |
| 验证集规则指标 | P2/P5/P6 指标改善或持平 | P2/P5/P6 指标恶化（模型在偏好训练中丢失了 SFT 收敛的格式能力） | 此为过优化信号——β 过小。立即停止，提升 β 至 0.5，或在 DPO 数据中混入 10% SFT 正例（防止灾难性遗忘） |
| 生成样本的格式退化 | 格式保持 canonical 结构，仅边界行为收紧 | JSON 合法率下降、出现新的格式错误 | 停止 DPO，回退到 SFT 权重。若 β 调整无效，考虑减少 DPO 偏好对数量或降低训练步数 |

**（3）评测驱动的中断准则。**

以下任一条件触发，暂停当前阶段，排查原因后再继续：

- SFT 后评测集法律概念命中率和清晰度指标相比 base 模型**无改善**（< 5% 提升）→ SFT 数据或训练配置有问题
- DPO 后三项规则指标（条文编号产出率/绝对化表述/拒答准确率）中任一项相比 SFT 权重**恶化 > 10%** → DPO 过优化，回退 SFT 权重
- 第一层知识保真度（DISC-Law-Eval）在 SFT 后 accuracy 下降 **> 5%** → 咨询体裁 SFT 严重挤压考试知识，需在 SFT 数据中混入知识保留样本
- 评测集 LLM-Judge 综合分在任一阶段后**下降 > 0.3 分**（5 分制）→ 该阶段的训练策略需要重新评估

### 2.4 训练数据集制作

> 本节只管训练数据集，评估数据集放到 2.5。两套数据集目标不同、生命周期不同、**必须严格隔离**——训练集里出现过的样本不能进评估集。

本节回答四个问题：① 训练集里有哪些样本，输入输出长什么样？② SFT/DPO 各按什么格式组织，如何适配 LLaMA-Factory？③ 样本从哪里来、怎么造、要多少条？④ 各类怎么配比、怎么做数据增强与版本管理？

#### 2.4.1 训练样本的三个来源

Phase 1 数据准备阶段确定了 SFT 数据方案（详见 Phase 1 报告），最终训练集由以下样本构成：

| 来源 | 条数 | 原始答案 | SFT 前处理 |
|------|------|---------|-----------|
| DISC-Law-SFT 保留 | 2,696 | DISC 原始（简短结论式） | **需重写**为 canonical 格式 |
| zixun_gpt4 保留 | 348 |律师-LLaMA 原始（公式化推理） | **需重写**为 canonical 格式 |
| 华律网 生成 | 4,404 | 无答案 | **待生成**（canonical 格式 prompt） |
| 手工构造拒答样本 | ~100 | 无答案 | **手工编写**，覆盖 1.2.1 类型 6 的三种子场景 |
| **合计** | **~7,600** | | |

**拒答样本（类型 6）的构造。** 手工构造约 100 条，覆盖 1.2.1 类型 6 的三种子场景：(a) 明显无关输入（"帮我写一首诗""今天天气怎么样"）；(b) 超出模型能力边界的法律相关请求（"帮我起草一份离婚起诉书""查一下 2024 年最新的工伤赔偿标准"）；(c) 需要执业资质才能回答的事项（"我的案子有多少胜算""帮我看看这份合同有什么法律风险需要修改"）。拒答样本的 output 统一为礼貌拒答 + 诚实说明边界（如"这是需要执业律师做的事情，我可以帮您分析这类问题涉及的法律要点，但无法代您完成"），不编造回答也不冷冰冰地拒绝。约 100 条的规模足够教会模型拒答的行为模式——拒答不需要像正类那样覆盖丰富的话题维度，样本的核心变量是拒答的**措辞多样性**（避免模型只学会一种固定的拒答句式）而非**场景多样性**。

重写 DISC 和 zixun 并非要把它们"抹平"为同一个 LLM 的单一风格，而是刻意设计的第三步：**对齐到一个中和了两种来源各自优点的 canonical 格式。**

DISC 和 zixun 的优缺点不对称且互补——DISC 的优点在于简洁、直接、不堆砌连接词，缺点在于缺少推理展开过程（41.7% 篇幅不足 200 字）；zixun 的优点在于推理链完整、分析层次分明，缺点在于公式化（"首先/其次/最后"占 31.3%）和套话收尾（32.4%）。设计初衷不是"A 向 B 看齐"，而是从两种来源中分别提取有用的部分——DISC 的简洁表达 + zixun 的推理深度——定义第三种格式作为对齐目标。canonical 格式的三段式结构（事实理解→法律依据+说理→结论建议）既保留了 zixun 的推理展开，又去掉了连接词模板；既保留了 DISC 的直接性，又补充了推理展开。

重写改变的是**表达形式**（结构、展开程度、连接方式），不覆盖**法律内容**（法律定性、适用依据、核心结论）。原 DISC 回答认为"适用《城乡规划法》而非《土地管理法》"——这个判断被保留；原 zixun 回答认为"彩礼返还要看共同生活时长和用途"——这个分析被保留。它们被写入同一个结构模板，但法律判断仍然是不同的。重写后的风格统一不是副作用，而是目标——我们本来就不想让模型学 DISC 的简短风格或 zixun 的公式化风格，两种风格本身都是有问题的。生成华律网答案的 prompt 已在 Phase 1 设计完成并通过 30 条抽样质检。

#### 2.4.2 数据规模决策：为什么是 ~7,600 条

SFT 数据规模不是越大越好，也不存在一个"刚好够"的精确数字。本项目的决策逻辑是从三个方向交叉验证的。

**（1）任务复杂度决定数据需求的量级。** 法律咨询 SFT 的任务形态是"有结构但不僵化"——输出不是固定 JSON（几百条正例即可收敛 Schema），也不是开放式创意写作（需要海量数据覆盖多样性）。300-400 字的规范化推理链，教会模型的是"按这个范式展开"的行为模式，而不是"逐字背诵法律条文"。从同类法律 SFT 项目的公开经验来看，DISC-LawLLM 使用了约 10,000 条咨询类样本达到可用效果，Lawyer-LLaMA 在数千条规模上完成了初步的法律咨询对齐。本项目的 canonical 格式比 DISC 更结构化（降低了对数据多样性的需求），比 zixun 更统一（降低了对数据清洗的需求），因此 ~8,000 条处于同类项目的经验区间内。

**（2）数据自然汇聚到这个量级。** DISC 保留 2,696 条 + zixun 保留 348 条 + 华律网生成 4,404 条 + 手工拒答样本 ~100 条 ≈ 7,600 条。其中 DISC 经 simhash 近重复过滤（去除 149 条近重复），zixun 婚姻家庭类经话题分层降采样（766→300，去除话题冗余），总规模从原来的 ~8,000 下调至 ~7,600。华律网 4,404 条的抽取过程（详见 Phase 1 分布平衡方案）已经排除了低质量、重复和广告问题，保留了 580,694 条清洗池中最具代表性的样本。

**（3）预算约束下的理性上限。** 华律网答案需要用 LLM 逐条生成，4,404 条已经是一个有意义的规模。如果需要大幅增加（例如从 8,000 到 20,000），新增的 12,000 条几乎全部需要走"华律网抽取 + LLM 生成 + 质检"的流程，时间成本和 API 调用成本会线性增长。在 8,000 条这个量级上，Phase 1 的抽样质检已经确认生成的答案达到可接受的格式一致性，可以认为数据质量（而非数量）是当前阶段的主要矛盾——优先保证 8,000 条的准确性、一致性和类别覆盖度，比追求更大数量更有价值。

**（4）数据规模的实验验证计划。** 文档阶段无法给出"X 条刚好够、X+N 条不再有提升"的精确结论——这是实验问题，不是分析问题。SFT 后将通过数据消融实验来验证：分别用 4,000 / 8,000 / 全部 条训练，比较评测指标随数据量变化的饱和曲线。如果 8,000 条相比 4,000 条有显著提升但相比全量接近饱和，则 8,000 是合理规模；如果全量相比 8,000 仍有大幅提升，则后续需追加数据。

#### 2.4.3 类别配比策略

法律咨询问题的真实分布高度不均衡，但配比策略不应人为放大这种不均衡。本项目的配比原则是：**直接跟随华律网 67.6 万条真实咨询的自然分布**，不做人为的核心/相邻分组和比例倾斜。

**（1）为什么跟自然分布走。**

此前考虑过将核心三类（劳动/合同/婚姻家庭）人为提升到 80% 的训练占比——理由是"这些类别推理模式具备共性、可以泛化到其他类别"。但这一假设未经实验验证，风险在于：债权债务（自然占比 15.5%）、人身侵权（13.9%）、交通事故（8.8%）在有真实用户需求的类别，如果被人为压到 1/3，模型在这些高频场景中的回答质量可能退化。华律网 67.6 万条真实咨询的分布本身就是用户需求结构的最客观反映——"用户更常问什么，模型就应该更会答什么"。

#### 2.4.4 为什么不做难例上采样

参考同类型项目中常见的一个做法是 SFT 阶段的难例上采样（hard-example over-sampling）——借用 OHEM 与 ADASYN 的思想，刻意提高难样本的训练占比。本节解释为什么在本项目中**不采用**这一策略。

**（1）难例上采样解决什么问题。** 它针对的是这样一种场景：数据中某类样本天然稀少，但其正确判断对任务至关重要。典型如参考文档 slot-extractor 中，用户说"好""可以""换一个"——这些短回复在字面上几乎相同，但在不同上下文中的含义截然不同（确认预约 / 修改需求 / 闲聊）。这类样本在 100 条对话中可能只有 3-5 条，如果不刻意提高占比，模型在训练中根本接触不到足够多的边界判断场景。

**（2）本项目没有这种"天然稀少但致命"的样本。** 法律咨询任务中需要模型掌握的每类能力——推理链展开、法律概念应用、条件化表述、多诉求拆解——都通过 canonical 格式的 SFT 数据**全覆盖**来教，而非依赖少数难例：

- **推理链展开**：每条 canonical 格式样本都包含完整的四段式推理链。模型不是从稀有样本中学推理结构，而是被 8,000 条正例均匀地训练出"回答应该这么展开"的行为模式
- **条件化表述（1.3.2 类型 2）**：信息不足时应该如何回应——这不是边界 case，而是 SFT 数据构造阶段就被设计进去的正例类型。训练集中信息不足的样本和信息充足的样本按自然比例混合，模型不需要从稀有样本里额外学习
- **多诉求拆解（1.3.2 类型 3）**：复杂案件的拆解分析同样通过正例覆盖，在数据构造阶段有意保留了同时涉及多个法律问题的样本

**（3）本项目真正"难"的问题，解法不在 SFT 上采样，而在 DPO。** 六个痛点中，P2（格式不规范）、P3（法律依据幻觉）、P5（建议空泛）、P6（过度确定性）的本质是**负向约束**——模型不应该做某事。SFT 的正例教学只能教"应该怎么做"，边界控制需要对比学习才能收紧。因此这些问题在 2.4.6 中通过程序化构造 DPO 偏好对来解决，而非在 SFT 阶段对某些样本做上采样。

P1（推理链缺失）和 P4（法律概念误用）是正向能力问题，但它们的解法在"确保每条样本都包含推理链"和"确保标签正确"，不在于把少数样本多做几遍。

> 一句话：**难例上采样适用于"正例天然稀少"的场景；本项目需要的不是更多遍的正例，而是"正例 vs 反例"的对比学习。前者 SFT 已全覆盖，后者是 DPO 的职责。**

#### 2.4.5 SFT 样本格式

每条样本的输入是用户的法律咨询问题，输出是 canonical 格式的法律咨询回答（300-400 字，含推理链）。适配 LLaMA-Factory 的 alpaca 格式：

```json
{
  "instruction": "你是一位专业的中国法律咨询顾问。请针对用户的问题，给出包含推理过程的法律咨询回答。回答应自然包含：理解用户处境 → 法律定性 → 法律依据与说理 → 结论与建议。引用法律名称时使用书名号，不写具体条文编号。不使用'首先/其次/最后'等标签化结构词作为全文框架。在建议部分可以用数字序号（"第一/第二/第三"）列举具体行动步骤，这属于功能性列举而非公式化结构。不编造案情细节和精确数据。",
  "input": "公司拖欠工资三个月，没有签劳动合同，现在要求我离职，我应该怎么办？",
  "output": "您提到公司拖欠三个月工资且未签劳动合同，现被要求离职，这涉及劳动报酬支付、未签合同的法律后果以及离职性质三个核心问题。\n\n在法律上，这属于典型的劳动争议……（约 350 字的 canonical 格式回答）"
}
```

`instruction` 字段固定为 canonical 格式的系统 prompt，与推理时保持一致（训练-推理分布对齐）。`input` 为用户问题原文，`output` 为规范化回答。拒答样本（类型 6）使用相同的 `instruction` 但 `output` 为拒答内容，不单独设拒答专用的系统 prompt——模型应通过输入内容本身判断是否需要拒答，而非依赖不同的 instruction 来切换行为。LLaMA-Factory 默认 `train_on_prompt=False`，仅对 `output` 段计算 loss。

#### 2.4.6 DPO 偏好对构造与配比

> **📝 最终结果（2026-08 训练收尾）：** 本节"规则扰动双源构造"方案在实际执行（Phase 5）中被证明质量差（P6 结尾模板化、P4 编造错配、P3 扰动失败），最终改用 **deepseek-chat 生成 chosen + SFT 真实输出作 rejected**（2019 对）。详见 [phase5-dpo-training-design.md](superpowers/specs/phase5-dpo-training-design.md) 与 [round1-dpo-data-redesign.md](superpowers/specs/round1-dpo-data-redesign.md)。本节原始设计思考保留存档。

DPO 偏好对无需人工标注。构造逻辑：将一条样本的 **chosen**（正确的 canonical 格式回答）与 **rejected**（存在特定错误的回答）配对。所有偏好对混合为单轮 DPO 训练——每个 rejected 定向对应一个痛点，但训练时不区分轮次。

适配 LLaMA-Factory 的 DPO 格式：

```json
{
  "prompt": "（同 SFT 的 instruction + input）",
  "chosen": "（正确的 canonical 格式回答）",
  "rejected": "（存在错误的回答）"
}
```

**（1）双源构造策略：程序注入 + 天然原始答案。**

如果 rejected 全部由程序化注入错误生成（如正则插入条文编号、替换法律名称），面试官可以质疑：模型只是学会了"别写正则能匹配到的特定模式"，换个形式可能还会犯。因此采用双源构造：

| 来源 | 做法 | 适用痛点 |
|------|------|---------|
| **程序注入** | 对一条 chosen 注入一种特定错误模式得到 rejected，每条 rejected 定向一个痛点 | P2（插入条文编号/标签词）、P3（替换法律名称）、P5（替换为套话收尾）、P6（插入绝对化表述） |
| **天然原始答案** | 使用 DISC/zixun **重写前**的原始回答作为 rejected，与之配对的 chosen 是同一问题重写后的 canonical 回答 | P1（DISC 原始缺推理链）、P2（zixun 原始含标签词）、P5（zixun 原始含套话）、P6（zixun 原始含绝对化表述） |

**天然原始答案作为 rejected 的合理性。** DISC 和 zixun 的原始回答本身就是需要修正的问题样本。将同一条问题的 canonical 重写版本作为 chosen、原始版本作为 rejected，构成"正确格式 vs 真实错误"的天然对比。两者的法律定性和核心结论一致（因为是同一问题的两种表达），差异集中在形式质量上，对比信号聚焦于"应该怎样表达"而非"应该得出什么结论"。

**天然原始答案的多重错误问题。** DISC 原始回答可能同时存在推理缺失（P1）和条文编号（P2），zixun 原始回答可能同时存在标签词（P2）、套话收尾（P5）和绝对化表述（P6）。对于这类"一个 rejected 带多个错误"的样本，按其主要错误模式归类（DISC 原始→主归 P1，zixun 原始→按最突出特征归属），但在训练中不作为混合信号处理——同一 rejected 存在多个错误时，它在多个痛点维度上都构成负样本，模型在对比学习中自然学会避免所有这些特征。这不是缺陷——真实场景中一个差的回答往往同时在多个维度上不合格，混合错误 rejected 恰好反映了这种真实分布。

**天然原始答案不适用于 P3。** DISC 和 zixun 中大部分编造的法律名称已在 Phase 1 清洗中移除，天然样本不足以覆盖法律依据幻觉的多样性，P3 全部依赖程序注入。

**（2）规模决策：为什么是 ~2,000 对。**

DPO 偏好对的数量不由 SFT 数据量机械推算，而是由错误模式覆盖度和任务复杂度共同决定。以下从业界参照和本项目决策两个层面展开。

**业界参照。** OpenAI 的 DPO 使用指南明确指出，偏好对应按"实际暴露的错误"配对，数量通常为数百到数千对，而非追求绝对规模。HuggingFace 2025 微调指南（philschmid《How to fine-tune open LLMs in 2025》）将 DPO 偏好对列为 SFT 的后续纠错手段，数量通常比 SFT 数据少一个数量级。同类后训练项目中，参考文档 slot-extractor 任务使用 ~300-500 对偏好对配 ~1,500 条 SFT 样本（比例约 1:3 到 1:5），其输出空间为固定 JSON Schema，错误模式高度可枚举。UltraFeedback 等通用偏好对齐数据集可达数万对，但那是面向通用对话质量的偏好对齐，与领域纠错型 DPO 的目的不同。

**本项目的决策逻辑。** 偏好对数量由三个因素共同确定：

第一，错误模式的丰富度。本项目 6 个痛点，每个痛点内部含 1-2 种可区分的错误子模式（如 P3 含"编造不存在法律"和"错用真实法律"两种）。如果每种子模式需要 100-300 对才能形成稳定的对比信号，总需求约为 1,200-2,400 对。P3（法律依据幻觉）需要更多——不仅错误类型多样（法律名称的组合空间远大于"有/没有条文编号"这种二元判断），且这一痛点对回答的可信度影响最大，应分配最多偏好对。

第二，输出空间的复杂度。参考文档的 slot-extractor 任务输出为固定 JSON，300 对即可覆盖主要错误模式。法律咨询回答的输出是 300-400 字的自然语言推理链，其错误表现形式比 JSON 字段错误更丰富——同样的"建议空泛"可以有几十种不同的措辞。因此偏好对数量需要适当高于结构化输出型任务。但同时，DPO 也不像 SFT 那样依赖样本多样性——偏好对的核心能力是对比，一条对比鲜明的偏好对比十条边界模糊的偏好对更有效。

第三，天然 rejected 的数量上限。DISC 和 zixun 保留数据中能提取的天然含错样本有限（DISC ~2,696 条原始回答、zixun 经降采样后约 348 条，其中含标签词/套话/绝对化表述的子集相应缩小），天然 rejected 合计约 300-500 对。程序注入的 rejected 可以按需生成，但不应无限膨胀——每条 chosen 配 1-2 条定向 rejected 即够，超过 3 条边际增益递减。

综合以上，本项目 DPO 偏好对预估为 **~1,500-2,500 对**，约为 SFT 数据量（~8,000 条）的 1/5 到 1/3。与参考文档的 slot-extractor 相比，数量更高，原因来自任务差异——法律咨询回答的输出空间比固定 JSON 更开放，每个痛点需要更多样的 rejected 才能覆盖不同的错误表现形式。

**（3）单轮配比：火力向最难纠的痛点倾斜。**

DPO 偏好对按痛点分配而非均匀铺开。P3（法律依据幻觉）是 SFT 最难收敛的痛点——教模型"该引用时不引用"和"引用错了不引用"需要更多样的对比信号——因此分配最多偏好对。P1（推理链缺失）SFT 正例已大量覆盖，分配最少。天然原始答案受限于数据源中实际含错样本数，数量不由设计决定。

| 构造来源 | 目标痛点 | 偏好对数量 | 说明 |
|---------|---------|-----------|------|
| 程序注入 | P3 法律依据幻觉 | **~600-800** | 火力集中：每条 chosen 配 2 条 rejected（编造+错用），约 300-400 条 chosen |
| 程序注入 | P5+P6 建议空泛/过度确定性 | **~400-600** | 每条 chosen 配 1-2 条定向 rejected |
| 程序注入 | P2 格式不规范 | **~200-300** | 二元约束，学习效率高，少量即可收敛 |
| 天然 | P1 推理链缺失 | **~150-200** | DISC 原始回答，受限于可用数量 |
| 天然 | P2+P5+P6 | **~150-300** | zixun 原始回答，部分样本混合多错误 |
| **合计** | | **~1,500-2,200** | |

**（4）双源策略的优势。**

约 20% 的 rejected 来自真实数据中的天然错误（DISC 的推理缺失、zixun 的标签词/套话/绝对化表述），而非全部由程序注入。天然 rejected 的关键价值不在于数量，而在于它们的存在证明了**偏好对不是在防正则**，而是在教模型区分"好的法律咨询回答"和"真实法律咨询场景中常见的坏回答"。程序注入覆盖的是天然数据中已被清洗干净的错误模式（如法律名称替换），二者互补。

**（5）与 2.2.4 痛点对齐表的关系。**

本节的双源构造策略导致 2.2.4 对齐表中 P1（推理链缺失）在 DPO 列从"无直接增益"变为"辅"。其余痛点对应关系不变。

#### 2.4.7 数据版本管理

训练数据集标注生成完成后冻结为一个带日期标识的版本（如 `sft_data_v20260720.jsonl`），对应的 DPO 偏好对标注生成脚本也版本化。后续任何修改（如新增类别样本、调整配比、修改 canonical prompt）均生成新版本文件，不覆盖旧版本。版本间差异通过 diff 工具可追溯。

> 一句话：**训练集 = DISC 重写 + zixun 重写 + 华律网生成 + 手工拒答样本，四源合一、canonical 格式统一、DPO 偏好对程序化构造、配比对齐华律网真实分布。**

#### 2.4.8 数据质量准入标准

SFT 数据在进入训练前，每条样本需要通过以下质量检查。检查分为硬性标准（可自动判定，不合格直接剔除或修正）和软性标准（LLM-Judge 辅助判定，不合格标记人工复审）。

**（1）硬性标准（自动检测，全量覆盖）。**

| 检查项 | 检测方式 | 不合格处理 |
|--------|---------|-----------|
| 篇幅范围 150-600 字 | 字符数统计 | 过短说明推理链不完整→重写；过长说明冗长→截断或重写 |
| 不含条文编号 | 正则：`第[零一二三四五六七八九十百千\d]+条` | 正则清洗后重检，无法自动清洗的剔除 |
| 不编造精确数字 | 检测"XX元""XX%"等精确数字模式，与用户问题交叉比对 | 回答中出现的数字必须在用户问题中出现过，否则剔除 |
| 法律名称不虚构 | 提取回答中所有《XX法/条例》实体，区分三类：(a) 现行有效且在白名单内→通过；(b) 已废止但曾真实存在（如"婚姻法""合同法"）→**放行但标记**，因基座模型预训练数据中含有这些名称，后训练不强制统一术语，法律分析的实质正确性优先于名称时效性；(c) 从未存在（如"中华人民共和国林业法"）→**硬性剔除**。白名单定义在 `process_data.py` | (a) 通过；(b) 放行+标记追踪；(c) 剔除或替换为"根据相关法律规定" |
| 不含标签化结构词 | 检测"首先/其次/再次/最后"出现在段落起头作为全文结构框架的情境（连续使用 ≥ 2 个视为违规）。"第一/第二/第三"出现在建议部分列举行动步骤时不视为违规 | 轻度违规（仅标签词本身多余）：正则删除标签词后段落自然连贯，直接删；重度违规（标签词撑起全文结构，删后段落断裂）：调用 LLM 局部重写（仅修违规段，不动其余内容）；均无法修复的标为 P2 模式问题，留作 DPO rejected |
| 不编造案情细节 | NER 提取人名/金额/时间/地点，与用户问题交叉比对 | 回答中多出的事实要素标为"疑似事实幻觉"，人工抽检确认后剔除 |

**（2）软性标准（LLM-Judge 辅助，按比例抽检）。**

> **📝 落地情况（2026-08）：** 硬性标准已落地（`validate_raw.py` + `clean_pipeline.sh` + `audit_validation.html` 人工审核）；**软性标准（LLM-Judge 全量打分）与 PPL 异常检测未落地**——实际清洗靠"规则校验 + 人工审核硬伤 + 拒答审核"替代。

| 检查项 | 判定方式 | 抽检比例 |
|--------|---------|---------|
| 推理链完整性 | 回答是否包含"事实理解→法律定性→说理→建议"四要素 | 全量 LLM-Judge 打分 |
| 法律概念准确性 | 回答中引用的法律概念是否与问题领域匹配 | 每类别抽 5% 人工交叉验证 LLM-Judge 的一致性 |
| 建议可执行性 | 回答是否给出了至少一个具体行动步骤 | 全量 LLM-Judge 打分 |
| 条件化表述 | 信息不足时是否使用了"如果…则…""可能/应当"等条件化措辞，而非确定性结论 | 信息不足类样本全量检查 |

**（3）准入阈值。**

全部硬性标准必须通过（不合格率目标为 0%）。软性标准按综合分判定——每条样本的 LLM-Judge 四个维度各打 1-5 分，平均分 < 3 分的标记为"需复审"，< 2 分的直接剔除。目标为全量样本通过硬性标准后，软性标准的不合格率 < 5%。

**（4）抽检策略。**

硬性标准全自动执行，覆盖 100% 样本。软性标准中，LLM-Judge 的打分全量执行——因为它也是自动化流程，边际成本极低。人工抽检仅用于验证 LLM-Judge 的一致性（每类别 5%，约 25-50 条），确认裁判模型的判定与人类判断是否对齐。若一致性低于 80%，需要调整裁判 prompt 或阈值后重检。

> **❓ 思考：为什么不强制统一法律名称的时效性？**
>
> 法律名称白名单将已废止的旧法（如"婚姻法""合同法"）标记为"放行但不鼓励"。这并非疏忽，而是有意不强制统一。背后的考量是领域 SFT 中一个已知问题：当 SFT 数据教授的术语偏好与基座模型预训练中内化的知识分布不一致时，强行覆盖可能引入不稳定性。
>
> 基座模型（如 Qwen2.5-7B）的预训练语料横跨多年，其中既包含民法典生效前的法律文本（"婚姻法""合同法"），也包含生效后的（"民法典"）。模型内部对同一法律概念存在两种合法称呼——这是预训练分布的客观结果，不是错误。SFT 如果强行统一为"民法典"，等于告诉模型"你原来知道的那种叫法是错的"——但模型对"婚姻法"这个概念的理解并非错误，只是术语版本不同。这种表面改名称、实际上与模型内部知识分布冲突的信号，可能导致模型在涉及婚姻家庭法时出现更多不稳定行为。
>
> 业内 LIMA、Alpaca 等工作同样表明：SFT 主要教会模型格式和风格，而非改写事实知识。如果某个"知识"（包括术语）在预训练分布中有广泛支撑，少量 SFT 样本很难可靠地覆盖它——强行覆盖的后果通常是模型在不同上下文间摇摆。本项目的定位是 1.3.3 的诚实边界：后训练改善的是形式质量，法律名称的术语版本差异不影响分析的正确性。真正要防的是编造（"中华人民共和国林业法"这种从未存在的名称），不是术语版本差异。因此白名单分级策略的核心逻辑：**防幻觉（c 类），放行旧术语（b 类），不强制统一。**

#### 2.4.9 迭代闭环：数据驱动的训练优化

2.4.2 提到当前约 7,600 条是一个合理的起步规模，但文档阶段无法给出"多少条刚好够"的精确结论。这个问题通过迭代闭环来解决：不是一次性构造完所有数据再训练，而是**先跑第一轮，用评测结果驱动数据补充方向和配比调整**。

**（1）为什么需要迭代。**

一次性构造数据的根本问题在于：构造阶段并不知道 SFT 后模型的实际弱项在哪。评测集在 2.5 中一旦冻结即不参与训练——它恰好可以充当"诊断工具"。SFT 第一轮→评测→发现"交通事故类问题推理链完整度明显低于其他类别"→回到华律网池子，针对交通事故类别多抽 200 条问题、生成答案、加入训练集→SFT 第二轮。这个循环的每一步都由评测数据驱动，而非训前的猜测。

**（2）迭代维度与判定标准。**

每一轮评测后，按以下维度诊断是否需要补数据：

| 诊断维度 | 判定方式 | 补数据策略 |
|---------|---------|-----------|
| 类别短板 | 某类别的 LLM-Judge 综合分显著低于均值（低 15% 以上） | 从华律网池子针对该类多抽 100-200 条，生成答案后加入 SFT 数据 |
| 痛点残余 | 某痛点的规则指标未达标（如条文编号产出率 > 2%、绝对化表述比例 > 5%） | 针对该痛点追加 DPO 偏好对 100-200 对 |
| 推理链退化 | 篇幅 < 200 字的回答占比在第一轮 SFT 后仍 > 20% | 检查该类别的 canonical 格式样本质量，修正问题样本后重新训练 |
| 过拟合信号 | 训练集上指标持续改善但验证集上不再改善或恶化 | 停止训练，不追加数据——问题不在数据量而在训练策略 |

**（3）迭代预算与停止条件。**

每轮迭代需要额外生成数据和重新训练，成本线性增长。预算约束下的停止条件：

- **性能饱和**：最近一轮迭代在评测集上的综合分提升 < 3%，说明当前数据规模和方法已接近天花板
- **预算耗尽**：累计 GPU 时数接近 200 元上限（2.3.3），不再追加训练轮次
- **收益递减**：某一维度连续两轮补数据后指标未改善，说明问题不在数据而在模型能力或方法——转而调整训练策略

**（4）预期迭代次数。**

参考同类项目经验，经过 1-2 轮迭代（首轮 SFT+DPO→评测→诊断→补数据→第二轮 SFT+DPO）通常能收敛到性能饱和点。第二轮迭代不需要从头构造——只在首轮弱项上有针对性地补数据（预估每轮追加 500-1,000 条 SFT 数据或 100-300 对 DPO 偏好对）。两轮预算控制在额外 5-10 GPU 小时内。

### 2.5 评估方案（含评估数据集制作）

> **关键设计前提（与训练目标一致）**：模型无 RAG 能力边界，评测体系不要求精确条文编号匹配。SFT 目标为学习法律咨询回答风格和"回答需要有法律依据"的行为模式，RL 目标为奖励正确的法律概念引用和惩罚条文编号产出。评测体系需与上述目标对齐——评测"依据合理性"而非"编号精确匹配"。

#### 2.5.1 评测体系总览：两层结构

| 层级 | 目的 | 数据源 | 评测方式 |
|------|------|--------|---------|
| 第一层：法律知识保真度 | 检测 SFT/RL 训练是否导致基础法律知识退化 | DISC-Law-Eval 客观题集（标准化法考选择题） | 复用官方评测脚本，对比 base vs 训练后模型 accuracy |
| 第二层：法律咨询质量 | 评测模型在真实咨询场景下的分析与建议能力 | 华律网真实咨询数据（按领域标签筛选） | 规则可验证指标 + LLM-as-Judge 无参考打分 |

两层各司其职：第一层不评估咨询能力，仅用于知识保真度回归测试；第二层是咨询质量的核心评估，与训练目标直接对齐。DISC-Law-Eval 主观评测集（300 条）经人工抽查发现场景与考试题重叠度高、部分 input-output 对应关系存在噪声，因此弃用，统一使用华律网真实咨询数据作为第二层评测集。

#### 2.5.2 第一层：法律知识保真度

**数据与工具**：DISC-Law-Eval 客观题集（来源为国家司法考试 NJE、CPA、律师资格考试 PAE、研究生入学考试 UNGEE 等标准化考试），直接复用官方 `eval/src/eval.py` 中的正则答案抽取逻辑与 ml3m 评测框架。不额外引入 lm-evaluation-harness（该框架无现成中文法律选择题 task 配置，自建 task 的工作量与直接复用官方脚本相当）。

**执行步骤**：
1. 小批量验证模型输出格式与官方正则的兼容性——经咨询体裁 SFT 后的模型倾向输出"先分析后作答"的长文本，可能与考试简洁作答格式不匹配。若抽取失败，通过调整 prompt（要求结尾单独输出"答案：X"）对齐正则模式，不改动评测脚本本身
2. 分别对 base 模型与训练后模型运行评测
3. 按题目难度分层（简单/中等/困难）与题型（单选/多选）分别统计 accuracy

**预期用途**：若训练后模型在客观题上出现掉点，定位原因为咨询体裁 SFT 数据对考试式简洁作答分布的挤压效应——而非知识遗忘，并提出在 SFT 数据中混入少量保留原始知识问答格式的样本作为缓解措施。

> **📝 落地情况（2026-08 补跑后）：** Layer 1 已补跑 SFT 与最终模型。结果：M0 29.2% → SFT V4 34.6%（+5.4pct）→ **DPO Round 5 V1 37.8%**（+8.6pct，DPO 阶段再 +3.2pct，知识未退化反而提升）。见 `results/sft_knowledge.json` 与 `results/dpo_v1_knowledge.json`。

#### 2.5.3 第二层：法律咨询质量

**数据来源与处理**：
- 数据源：华律网真实咨询数据（`question_2.json`，已清洗至 580,694 条），字段包含 `title`（领域标签）与 `question`
- 筛选方式：按领域标签筛选，覆盖 11 个分类，每个分类按自然分布比例抽样
- **只使用 question，不使用任何回答内容**：真实律师回复存在广告引流、内容过短等噪声，不适合作为参考答案；且在咨询体裁下，评测目标是"依据合理性"而非与某条参考答案的语义匹配度，因此统一采用无参考 LLM-as-Judge 打分
- 抽样时保留部分信息不完整的真实咨询样本，用于观察模型是否具备追问和条件化表述行为
- **严格隔离**：评测集样本的 question 不得出现在训练集中

**评测指标**：

（A）规则可验证指标（可编程、低成本迭代）：

**三项硬指标：**

1. **条文编号产出率**：正则抓取"第X条"/"第X款"等具体条文号声称模式，检测模型是否在 instruction 明确要求"不写条文编号"的情况下仍输出了条文级别的引用。注意：**不做真假判断**——基座模型可能记住了正确的条文，但在无 RAG 约束下无法验证，输出即视为指令违规。设计依据见 1.3.1

2. **绝对化表述比例**：正则匹配"一定/必然/肯定/毫无疑问/绝对"等绝对化措辞。法律咨询场景下，模型不应给出绝对化结论

3. **拒答检测**：在评测集中混入约 30 条类型 6 样本，检测模型是否在该拒答时硬给答案（false negative in refusal）。同时检测正类样本（类型 1-5）中模型是否无故拒答（false positive in refusal）。两条线汇总为拒答准确率

**辅助统计（仅计比例，不参与硬扣分）：**

4. **套话收尾比例**：检测"建议咨询专业律师""请咨询律师"等表述的出现比例。纯正则无法区分"诚实边界声明"（给了具体建议后补充咨询建议）和"偷懒甩锅"（通篇空话后以咨询律师收尾），因此仅做辅助统计。正式判断交给 LLM-Judge 的"建议可执行性"维度

**为何不设"结构完整性"规则指标：** canonical 格式明确禁止"首先/其次/最后"等标签化结构词。用关键词匹配检测结构完整性，与 canonical 格式的设计自相矛盾——结构完整性应体现在自然段落过渡的连贯性上，而非标签词的存在。此维度交给 LLM-Judge 的"清晰度"评估

5. **法律概念/要点命中率**：替代条文编号命中率。每条数据人工标注 2-3 个应命中的法律概念（如"夫妻共同财产""经济补偿金""过错赔偿责任"），用关键词/同义词表匹配。此指标归入规则可验证指标，但独立于上述三项硬指标和辅助统计

（B）LLM-as-Judge 指标（4 维 + 1 行为维度，Checklist + 0-3 量表）

LLM-as-Judge 评测维度的设计参照了以下工作：DISC-Law-Eval 的三维框架（准确性、完整性、清晰度）；DeCE（Yu et al., EMNLP 2025）的 Precision + Recall 解耦评估（r=0.78 vs 传统 r=0.35）；Hagan（JURIX 2024）关于可操作性的用户研究；shopping-grpo 的 satisfied/violated/unknown 判定体系和四面板独立报告设计。

**维度体系**：准确性+完整性用 Checklist 对比参考答案（satisfied/violated/unknown），清晰度+建议可执行性用 0/1/2 独立打分，信息审慎度仅对类型 2/6 评测。四个面板独立报告，不合成唯一总分。

| # | 维度 | 方式 | 量表 | 适用 |
|---|------|------|------|:---:|
| 1 | 准确性 | Checklist vs 参考答案 | satisfied / violated / unknown | 全部 |
| 2 | 完整性 | Checklist vs 参考答案 | satisfied / violated / unknown | 全部 |
| 3 | 清晰度 | LLM-Judge 独立打分 | 0-3 | 全部 |
| 4 | 建议可执行性 | LLM-Judge 独立打分 | 0-3 | 全部 |
| +1 | 信息审慎度 | LLM-Judge 打分 | 0-3 | 仅类型 2/6 |

#### 2.5.3 评测 Prompt 设计原则：Bare Prompt 评测

**核心决策：训练用详细 prompt，评测用 bare prompt。** 评测的目的是测量模型自身能力，而非测量模型执行指令的能力。如果在评测 prompt 中告知模型"应该如何组织回答、不应做什么"，则无法区分模型的真实能力提升与指令执行能力提升。

**参考依据。** DISC-LawLLM（复旦，2024）在评测时使用的 system prompt 仅为一句话 `你是一名中国法律专家。`，无任何格式要求、字数限制或行为指导。其 403K SFT 数据通过详细的 Legal Syllogism Prompting 策略生成，但推理评测时仅使用裸身份标签。Dominguez-Olmedo et al.（2024）提出 *Training on the Test Task Confounds Evaluation*，指出在评测中使用与训练相同的指令格式会导致模型能力的高估，因为评测测量的是指令执行能力而非真实能力。Train-Before-Test（2025）在 24 个基准、61 个模型上验证了标准化 prompt 对公平评测的必要性。

**本项目实践。** M0 基线阶段同时跑了 full prompt 和 bare prompt 两版推理：

| 维度 | Full Prompt | Bare Prompt |
|------|------------|-------------|
| 评测 prompt | 300 字详细指令（结构、字数、格式要求） | `你是一名中国法律专家。` |
| 测量对象 | 模型能否执行详细指令 | 模型自身具备什么法律咨询能力 |
| 格式合规 | 人为注入，非模型能力 | 反映真实基线水平 |
| 跨版本可比性 | 低——SFT 后改善可能是"更会听指令" | 高——改善反映真实能力提升 |

> **📝 修订 (2026-07-30):** 评测 prompt 从 full prompt 改为 bare prompt。`eval/prompt_template.py` 保留两份常量：`EVAL_INSTRUCTION`（评测用，bare）和 `TRAIN_INSTRUCTION`（训练数据生成用，full）。已有 full prompt 基线结果归档为 M0-full 参考，bare prompt 结果作为正式 M0 基线。

**法律概念标注的人力方案。** Kondo et al.（ISWC 2024）实验表明 GPT-4 在日本法院判决书的法律条文要素抽取中达到 Recall 0.89 / Precision 0.87，说明 LLM 预标注法律概念在精确率上接近可接受水平；但 Carnat et al.（2024，i-lex）的结论是"LLM 可以降低标注成本但不是替代品，混合方案是业界标准"。本项目的标注策略：与场景类型标注、Judge 校准合并到同一 30 条试点，LLM 先预标注法律概念，人工逐条核验并计算预标注精确率。如果精确率 > 85%，推广到全量评测集并仅人工抽检 20%；如果不足，缩小到 LLM 预标注 + 全量人工修正。总人力预估根据试点结果确定，不作为硬性预算承诺。

评测集一旦冻结，除非发现标注错误，否则不再修改——即使后续训练集版本迭代，评测集始终保持不变以确保跨版本可比性。
