## 1. 模块划分与数据流

### 1.1 数据流

```
                       [五张数据规格卡]  ← 人工审核关口（本文档第 2 节）
                              │  审核通过后卡片 = 生成 prompt 模板
                              ▼
      deepseek-chat  ──生成──►  raw 原始样本    ──► data/raw/v0.1/*.jsonl
      (卡1/2/3/4)                   │
                              ┌─────┴──────┐
                        (纯规则渲染)    (纯规则扰动 + 天然原始)
                              ▼                ▼
                      SFT Alpaca 样本    DPO preference 对
                              │                │
                              ▼                ▼
                    data/processed/sft/v0.1/  data/processed/dpo/v0.1/
                              └──────┬─────────┘
                                     ▼
                          三级质量校验器
                                     ▼
                     train/val 分层切分 + 指纹隔离检查 + 版本登记
                                     ▼
                       dataset_info.json（LLaMA-Factory 注册）
```

**关键洞察（来自参考文档）**：真正要生成、要人工审核的只有一份 raw 原始数据集。SFT 与 DPO 都只是拿 raw 做机械格式变换——SFT 把 raw 渲染成 Alpaca 格式，DPO 把 raw 的 `answer` 作为 chosen、注入错误作为 rejected。两者都不新增业务内容。因此人工审核重心 100% 落在五张规格卡。

### 1.2 模块表

| # | 模块 | 位置（拟） | 职责 | 输入 | 输出 |
|---|------|-----------|------|------|------|
| 1 | 生成器 | `scripts/build_sft_raw.py` | 按五张卡组装 prompt，调 deepseek-chat，产出 raw 样本 | 华律网问题 / DISC原始 / zixun原始 | `data/raw/v0.1/{card1..4}.jsonl` |
| 2 | raw 校验器 | `scripts/validate_raw.py` | 每条 raw 过篇幅/条文编号/标签词/法律名称白名单/案情编造检查 | raw JSONL | 校验报告 + 违规列表 |
| 3 | SFT 渲染器 | `scripts/render_sft.py` | raw → Alpaca 格式 `{instruction,input,output}` | raw JSONL | `data/processed/sft/v0.1/train.jsonl` |
| 4 | DPO 扰动器 | `scripts/perturb_dpo.py` | 按 `dpo_targets` 路由，规则注入错误生成 rejected | raw JSONL | `data/processed/dpo/v0.1/train.jsonl` |
| 5 | 拒答构造 | `scripts/build_refusals.py` | Prompt D 参数化生成 ~100 条拒答样本 | 子场景参数 + user_input 变体 | `data/raw/v0.1/card5_refusals.jsonl` |
| 6 | 隔离检查 | `scripts/check_isolation.py` | 训练样本 vs `eval_v1.jsonl` 指纹去重 | 训练集 + 评测集 | 隔离报告（重叠=报错） |
| 7 | 切分+版本 | `scripts/finalize_dataset.py` | 9:1 分层切 train/val、写版本卡、生成 `dataset_info.json` | processed 数据 | `dataset_info.json` + 版本卡 |
| — | CLI 编排 | `scripts/build_dataset.sh` | 一条命令串起 1→7，支持 `--smoke` 小样冒烟 | — | 全部 |

### 1.3 风险建模

三个风险各由一个可独立测试的模块承接：

- **法律名称幻觉风险**（deepseek-chat 可能编造不存在的法律名称）→ 模块 2 raw 校验器，白名单过滤。
- **扰动器正确性风险**（rejected 必须"格式正确但决策错误"，不能是乱码）→ 模块 4 DPO 扰动器，验收项要求扰动后的 rejected 仍过篇幅/格式检查。
- **训评污染风险**→ 模块 6 隔离检查，指纹硬去重。

## 2. 五张数据规格卡

### 卡 1/5：华律网 · 信息充分 — 从零生成完整推理链

**① 业务情况**

用户问题包含足够的案件事实，诉求明确。模型从零生成 canonical 格式回答。这是五张卡中数量最大的——约 3,700 条。没有参考答案可以依赖，法律分析完全由 deepseek-chat 自主生成，质量门需要最严格的 prompt 约束。

**② 要素清单**

| 规则 | 具体要求 |
|------|---------|
| **必须有** | 四段式逻辑覆盖（理解用户处境 → 法律定性 → 法律依据与说理 → 结论与建议），不要求显式分四段但逻辑上要完整；引用至少一个法律名称并使用书名号 |
| **必须没有** | 条文编号（如"第X条"）；全文框架标签词（"首先/其次/最后"）；编造的用户未提及的案情细节；编造的精确数据（赔偿金额、百分比、具体时效天数等）；绝对化措辞（"一定/肯定/必然"） |
| **篇幅** | 200-450 字 |
| **不确定时** | 说"根据相关法律规定"，不得编造不存在的法律名称 |
| **建议部分** | 可以用数字序号（"第一/第二/第三"）列举行动步骤，这属于功能性列举而非公式化结构 |
| **法律结论** | 来自 deepseek-chat 自主生成——质量门用法律名称白名单检查，但不验证结论本身（职责边界见 spec 1.3） |

**③ raw 原始示范**

```json
{
  "id": "sft_card1_0001",
  "card": 1,
  "scenario_type": 1,
  "source": "hualv_generated",
  "generator_model": "deepseek-chat",
  "category": "劳动与工伤",
  "dpo_targets": ["P3", "P5", "P6"],
  "question": "公司拖欠工资三个月，没有签劳动合同，现在要求我离职，我应该怎么办？",
  "answer": "您提到公司拖欠三个月工资且未签劳动合同，现被要求离职，这涉及劳动报酬支付、未签合同的法律后果以及离职性质三个核心问题。\n\n在法律上，这属于典型的劳动争议。根据《劳动合同法》，用人单位与劳动者建立劳动关系应当签订书面合同。超过一个月不满一年未签的，应当向劳动者每月支付二倍的工资。公司拖欠工资的行为违反了按时足额支付劳动报酬的法定义务。\n\n现公司要求您离职，需要区分是协商解除还是单方辞退。如果是无正当理由单方辞退，属于违法解除劳动合同，您有权主张赔偿金。\n\n建议您尽快做三件事：收集工资记录、考勤、聊天记录等工作证据；向当地劳动监察大队投诉；申请劳动仲裁主张拖欠工资、未签合同的双倍工资差额以及违法解除的赔偿。注意劳动仲裁有一年时效，从您知道权利被侵害之日起算。"
}
```

**④ SFT 渲染规则**

- 格式：LLaMA-Factory Alpaca（`instruction` + `input` + `output`）
- `instruction`：固定为 canonical 系统 prompt（与推理部署时一致）
- `input`：`question` 字段原文
- `output`：`answer` 字段
- 训练配置：`train_on_prompt=false`，仅对 `output` 段计算 loss

**⑤ DPO 可派生类型**

| 痛点 | 扰动方式 | 示例 |
|------|---------|------|
| **P3（法律依据幻觉）** | 替换法律名称：(a) 错用真实法律：`《劳动合同法》` → `《合同法》`；(b) 编造不存在法律：→ `《中华人民共和国劳动保障法》` | "根据《中华人民共和国劳动保障法》…" |
| **P5（建议空泛）** | 把具体行动步骤替换为笼统收尾 | "建议您咨询专业律师，具体情况以实际为准" |
| **P6（过度确定性）** | 在结论中插入绝对化措辞 | "您一定能获得双倍工资赔偿和违法解除赔偿金" |

### 卡 2/5：华律网 · 信息不足 — 从零生成条件化回答

**① 业务情况**

用户问题缺少关键事实（缺时间线、证据情况、具体关系等），无法确定基本法律关系或给出确定结论。模型需识别信息缺口，基于已有信息做有限分析，使用"如果…则…""若能证明…则可能…"等条件化表述。禁止因为信息不足就把整篇回答变成纯提问——要先基于已有信息给初步分析，再指出缺口。

约 700 条。Prompt 比卡 1 多一层约束：条件化思维 + 拒绝绝对化。few-shot 示例需要是一条信息不足场景下的正确回答。

**② 要素清单**

| 规则 | 具体要求 |
|------|---------|
| **必须有** | 明确指出缺少什么关键信息；至少一处条件化表述（"如果/若/可能/取决于/在…情况下"）；基于已有信息的初步分析（不因为缺信息就什么都不说） |
| **必须没有** | 绝对化结论（"一定/肯定/必然/毫无疑问"）；编造用户未提供的案情细节以填补信息缺口；整篇变成纯提问列表（"请提供XX、请提供YY"）而没有任何分析 |
| **篇幅** | 150-400 字（可以比信息充分略短，因为要留空间给条件化表述而非硬结论） |
| **其余** | 同卡 1 的格式约束（无条文编号、无框架标签词等） |
| **法律结论** | 同卡 1 的风险边界——结论由 deepseek-chat 自主生成，不逐条验证 |

**③ raw 原始示范**

```json
{
  "id": "sft_card2_0001",
  "card": 2,
  "scenario_type": 2,
  "source": "hualv_generated",
  "generator_model": "deepseek-chat",
  "category": "交通事故",
  "dpo_targets": ["P6", "P4"],
  "question": "你好，律师我在大桥头快驶出去了闯了红灯",
  "answer": "您提到您在大桥头闯了红灯，但目前缺少一些关键信息来做出完整判断。\n\n闯红灯属于违反交通信号灯的行为，根据《道路交通安全法》，通常会被处以罚款并记分的行政处罚。如果您尚未收到罚单，可能需要等待交管部门通过电子监控系统自动识别并发出处罚通知。\n\n但您的具体情况取决于几个重要因素：是否发生了交通事故、是否有人员受伤、是否已被交警现场查处。如果当时被交警拦下并开具了处罚决定书，处理方式与电子监控抓拍有所不同。如果发生了事故，责任认定会更加复杂。\n\n建议您先确认是否已收到罚单或处罚通知，以及当时是否有事故后果。如果能提供这些信息，可以为您进一步分析处罚的可能范围和应对方式。"
}
```

**④ SFT 渲染规则**：同卡 1。`instruction` 固定为 canonical 系统 prompt。

**⑤ DPO 可派生类型**

| 痛点 | 扰动方式 | 示例 |
|------|---------|------|
| **P6（过度确定性）** | 条件化表述改为绝对化结论 | "您肯定会被罚款 200 元并扣 6 分，这属于最严重的交通违法行为" |
| **P4（编造缺失事实）** | 在回答中补充用户没说的案情细节 | "您在闯红灯时发生了追尾碰撞，前车已经报警处理…" |

### 卡 3/5：DISC 重写 — 保留结论 + 补充推理链

**① 业务情况**

DISC-Law-SFT 原始回答是简短结论式（41.7% 篇幅不足 200 字，88.2% 推理信号 ≤ 1），例如"根据《城乡规划法》，农田建棚属于违法建筑"——法律 + 结论，中间无推演。

模型需要将这类回答展开为完整 canonical 格式，但**必须保留原始回答的法律判断**（法律定性、适用依据名称、核心结论）。重写只改变**表达形式**（补充事实理解段落、展开法律说理、添加可操作建议），不覆盖法律内容。原始回答中如果引了某个法律名称，重写后仍然引用该名称——不准换成别的。

约 2,696 条。需要独立 prompt：输入包含原始回答，明确指示"保留以下法律判断，只改写表达方式"。

**② 要素清单**

| 规则 | 具体要求 |
|------|---------|
| **必须有** | 完整四段式推理链；法律名称和核心结论与原始回答一致（用 LLM 交叉检查） |
| **必须没有** | 改变了原始回答的法律定性（原本说"适用城乡规划法"不能变成"适用土地管理法"）；条文编号（DISC 原始可能含有，重写时必须去掉）；框架标签词 |
| **可能需要补** | 事实理解段落（DISC 原始通常直接从法条开始）；可操作建议（DISC 原始通常以结论收尾不给建议） |
| **篇幅** | 200-450 字（原始 50-150 字需要大幅展开，但不过度膨胀） |
| **红线** | 重写后的法律结论与原始不一致 → 硬性剔除，回退到原始回答 |

**③ raw 原始示范**

```json

  "card": 3,
  "scenario_type": 1,
  "source": "disc_rewrite",
  "generator_model": "deepseek-chat",

  "dpo_targets": ["P1", "P2"],
  "original_answer": "根据《城乡规划法》，农田建棚属于违法建筑。",

**④ SFT 渲染规则**：同卡 1。`instruction` 固定为 canonical 系统 prompt。

**⑤ DPO 可派生类型**

| 痛点 | 扰动方式 | 示例 |
|------|---------|------|
| **P1（推理链缺失）** | 把 canonical 重写版本作为 chosen，原始 DISC 简短回答作为 rejected | chosen=上面 300 字完整回答，rejected="根据《城乡规划法》，农田建棚属于违法建筑。" |
| **P2（格式不规范）** | 在重写版本中插入条文编号 | 在 have 回答中插入"第65条" |

### 卡 4/5：zixun 重写 — 保留结论 + 去公式化

**① 业务情况**

zixun_gpt4 原始回答是公式化长推理（31.3% 含标签词"首先/其次/最后"，32.4% 套话收尾）。与 DISC 相反——zixun 已经有推理链，不需要"补"，需要"修"。

模型需要：(a) 保留原始回答的法律结论和分析核心；(b) 去掉"首先/其次/最后"等标签词，改为自然段落过渡；(c) 把套话收尾（"具体情况需要根据法律和事实进行综合判断"）替换为具体可操作建议；(d) 去掉绝对化措辞。

约 348 条。和卡 3 一样，法律结论来自原始回答——不改内容只改形式。但改的是不同的形式问题（公式化 vs 简短）。

**② 要素清单**

| 规则 | 具体要求 |
|------|---------|
| **必须有** | 法律结论与原始一致；自然段落过渡（无"首先/其次/最后"框架）；具体可执行建议（替代原来的套话收尾） |
| **必须没有** | 标签化结构词残留；套话收尾（"建议咨询专业律师""以实际情况为准"——除非前面已经给了足够具体的建议后作为补充声明）；绝对化措辞（zixun 21.1% 含） |
| **可能需要调整** | 篇幅可能比原始缩短——zixun 去标签词和套话后通常自然回到 300-400 字 |
| **红线** | 清标签词时不能把有内容的话也删了——只删标签词本身，不删它后面的内容 |

**③ raw 原始示范**

### 卡 5/5：拒答 — LLM 参数化生成

**① 业务情况**

用户输入超出法律咨询范畴。模型需礼貌拒答并诚实说明边界。通过 Prompt D 参数化生成，覆盖不同子场景和措辞变体。约 79 条（生成 100 条，审核删除 21 条"不应拒答"）。核心质量指标不是覆盖度而是**措辞多样性**——通过参数化变体避免模型只学会一种固定拒答句式。生成后跑嵌入聚类去重验证多样性。

**② 要素清单**

| 规则 | 具体要求 |

| **必须有** | 礼貌拒答；诚实说明为什么不能做这件事；提示能代替做的事情（如果可以的话，如"我可以帮您分析这类问题涉及的法律要点"） |

## 3. 四个生成 Prompt

### Prompt A：从零生成（华律网 · 卡 1 + 卡 2）

**适用场景**：给一个问题，没有参考答案。模型从零写出 canonical 格式法律咨询回答。

```
【System Prompt】

你是一位专业的中国法律咨询顾问。你的回答需要体现清晰的法律推理过程，让用户不仅知道"结论是什么"，还能理解"为什么是这个结论"。

【回答结构】
你的回答应自然包含以下要素（用自然段落过渡，不要用标签分隔）：
1. 理解用户处境 — 用一两句话概括你理解到的核心问题
2. 法律定性 — 这个问题在法律上属于什么范畴，涉及哪些法律关系
3. 法律依据与说理 — 引用适用法律的名称（如《民法典》《劳动合同法》），说明该法律为什么适用、如何适用到用户的具体情况
4. 结论与建议 — 给出明确、可操作的后续步骤

【格式要求】
- 篇幅控制在 200-450 字
- 语言专业但易懂，面向普通用户
- 引用法律名称时使用书名号（如《劳动合同法》），不给出具体条文编号（如"第X条"）
- 不确定的法律名称不要编造，可以说"根据相关法律规定"
- 严禁编造任何精确数据（赔偿金额、统计数字、百分比、年份标准等），可以说"具体金额需根据当地标准计算"
- 严禁编造用户未提及的案情细节
- 不使用"首先/其次/再次/最后"、"大前提/小前提/结论"等标签化结构词作为全文框架
- 在建议部分可以用数字序号（"第一/第二/第三"）列举具体行动步骤，这属于功能性列举

【信息不足时的处理】
- 如果用户提供的信息不足，不要编造缺失事实，也不要整篇只提问
- 基于已有信息给出初步分析，用"如果…则…""若能证明…则可能…""取决于…"等条件化表述
- 明确指出需要补充哪些信息，以及为什么需要这些信息

【信息充足时的处理】
- 给出完整的法律分析和具体的行动建议
- 推理过程要完整，不跳步，不一步到位式下结论
- 结论要有依据支撑，不给绝对化预测（"一定/肯定/必然"）
```

```

## 4. 转换方法

### 4.1 raw → SFT（Alpaca，纯规则渲染）

五张卡共用同一渲染规则——raw 的 `question` → Alpaca `input`，raw 的 `answer` → Alpaca `output`。`instruction` 固定为 canonical 系统 prompt，与推理部署时一致：

```json
{
  "instruction": "你是一位专业的中国法律咨询顾问。请针对用户的问题，给出包含推理过程的法律咨询回答。回答应自然包含：理解用户处境 → 法律定性 → 法律依据与说理 → 结论与建议。引用法律名称时使用书名号，不写具体条文编号。不使用'首先/其次/最后'等标签化结构词作为全文框架。在建议部分可以用数字序号列举具体行动步骤。不编造案情细节和精确数据。",
  "input": "<question>",
  "output": "<answer>"
}
```

训练配置：`train_on_prompt=false`，仅对 `output` 段计算 loss。卡 5（拒答）使用**同一 `instruction`**——模型应通过输入内容判断是否需要拒答，而非依赖不同的 system prompt。卡 6（知识问答）使用独立的轻量 instruction（Prompt E）——模型应通过 instruction + 问题类型判断何时使用简洁模式。

> **§3 生成 Prompt 与本节的 SFT instruction 是什么关系**：§3 的四个 Prompt 是告诉 deepseek-chat 如何生成 raw 答案——它们是数据构造工具，包含详尽的格式说明、few-shot 示例和条件化约束。本节 §4.1 的 `instruction` 是训练数据中教给模型的东西——它更精简，与推理部署时一致。两者不要求逐字对齐：生成 prompt 可以比 inference prompt 更详细，因为生成时需要更强的格式约束；但核心格式规则（无条文编号、无框架标签词、四段式推理）必须一致。

### 4.2 raw → DPO（Alpaca preference，程序注入 + 天然原始）

> **📝 补记（Phase 5 后）：** 本节设计的"规则扰动"DPO 方案（P2-P6 程序注入 + 天然原始）在实际执行时被证明质量差——P6 结尾模板化（80% 同结尾）、P4 编造错配、P3 扰动失败（chosen≈rejected）。Phase 5 最终改用 **deepseek-chat 生成 chosen + SFT 真实输出作 rejected** 的方案。本节原始设计思考保留存档，最终方案见 [phase5-dpo-training-design.md](phase5-dpo-training-design.md) 与 [phase-05 log](../../project-log/phase-05-dpo-training/log.md)。

DPO 行复用 SFT 的 `instruction` + `input`，`chosen` = raw 的 `answer`，`rejected` 由两种来源派生。

DPO 的信号是**上下文绑定的**——chosen 和 rejected 共享同一条 `instruction + input`（同一条用户问题）。模型学到的是「对于*这个具体的案例*，chosen 的表述比 rejected 更好」，而不是全局偏好。P3 不会导致模型"偏好《劳动合同法》"——在劳动争议的 rejected 中《合同法》出现 600 次，但在合同纠纷的 chosen 中《合同法》仍然正常出现。DPO 不做全局法条排名，做的是「给定这个问题，哪个回答更好」。

> **重要限定**：真正的风险不在 DPO，在 SFT。如果 SFT 数据中某些问题被错误地引了不相关的法律名称作为 chosen，DPO 的 reference model（SFT 权重）已将错误内化。这又回到 spec 1.3 的诚实边界——SFT 教的是格式不是内容，法律正确性由基座模型预训练兜底。

#### 4.2.1 来源 A：程序注入（按痛点分算法）

每条算法按「前提 → 改哪些字段 → 连带同步 → 边界/失败处理」定义。

**P3 法律依据幻觉（最主要，~600-800 对）**

前提：chosen 的 answer 中包含至少一个《XX法/条例》引用。

- **P3-a（错用真实法律）**：把 chosen 中的一个法律名称替换为「名称相近但适用场景不同的真实法律」。预置混淆对表，如 `{"《劳动合同法》": "《合同法》", "《工伤保险条例》": "《医疗保险条例》", "《民法典》": "《民事诉讼法》", "《道路交通安全法》": "《道路运输条例》", "《消费者权益保护法》": "《产品质量法》"}`。如果 chosen 中的法律名不在混淆对表里，回退到 P3-b。

- **P3-b（编造不存在法律）**：把 chosen 中的一个法律名称替换为「看起来像真的但实际不存在的法律名称」。预置假名池，如 `["《中华人民共和国劳动保障法》", "《中华人民共和国交通管理法》", "《中华人民共和国消费者权益保障法》", "《中华人民共和国工伤赔偿法》"]`。格式保持书名号、保持"中华人民共和国"前缀、保持"法/条例"后缀——让编造的名称看起来合规。

连带：只改法律名称，不改其余文字。rejected 其余部分与 chosen 完全一致。

边界：如果 chosen 中没有引用任何法律名称（通常不会），该条不派生 P3。假名池中的名称必须经白名单确认不存在（预检一次）。

**P6 过度确定性（~300-400 对）**

前提：chosen 中包含条件化表述（"如果/若/可能/取决于/在…情况下"），或结论部分没有绝对化措辞。

- **P6-a（条件→绝对）**：找到 chosen 中的条件化表述，改为确定结论。如"如果发生了事故，责任认定会更加复杂" → "您造成了事故，必须承担全部责任"。同时在全文中追加至少一处"一定/肯定/必然"。

- **P6-b（软化→硬化）**：如果 chosen 中没有明显的条件化表述但结论措辞偏软，在结论末尾追加绝对化断言。如文末加一句"根据法律规定，您肯定能获得赔偿"。

连带：改了结论措辞后，允许全文出现逻辑自相矛盾——真实坏回答往往前文说"取决于具体情况"后文说"您肯定能赢"。

边界：如果 chosen 本身已经绝对化（理论上不该出现），不派生 P6。

**P5 建议空泛（~200-300 对）**

前提：chosen 中包含至少一个具体可执行的建议（如"向当地人社局提交工伤认定申请"）。

改法：把建议段落整体替换为笼统套话。预置套话池：`["建议您咨询专业律师，以实际情况为准", "具体情况需要根据法律和事实进行综合判断", "建议您通过法律途径维护自己的合法权益", "可以咨询当地相关部门了解具体情况"]`。

连带：其余内容（理解处境、法律定性、说理）保持不变——只换建议段。rejected 是"分析看起来还行但到了建议就甩锅"的典型坏回答。

边界：如果 chosen 的建议段本身就是套话（卡 4 重写后不应出现但万一），不派生 P5。替换后检查 rejected 篇幅是否仍在 100 字以上（避免整条过短）。

**P2 格式不规范（~100-150 对，程序注入部分）**

前提：chosen 中没有框架标签词（canonical 格式天然没有）。

改法：在 chosen 的段落起头插入"首先/其次/最后"作为全文框架。不是替换，是插入——在每段开头加标签词，让整篇看起来像公式化模板。

边界：只在 ≥ 3 段的回答上做（2 段以下的短回答加标签词反而不自然）。

**P4 编造事实（~100-150 对）**

前提：chosen 属于卡 2（信息不足），且没有编造用户未提及的细节。

改法：在 chosen 的"理解用户处境"段开头，补充一句用户没说过的话。如原问题只说了"闯了红灯"，在回答开头加"您在闯红灯时发生了追尾事故，对方车辆受损严重……"。

连带：补充的事实必须和原问题在同一语义域（交通事故补充碰撞细节、劳动纠纷补充工资数额），不能加完全不相关的信息。

边界：如果 chosen 已经补充了缺失事实提示（卡 2 正确行为），改法是把提示改成断言（"缺少是否发生事故的信息" → "确实发生了事故"）。

#### 4.2.2 来源 B：天然原始回答（作为 rejected）

DISC 和 zixun 重写前的原始回答自然含错——不需要程序注入：

| 来源 | 作为 rejected 的理由 | 适用痛点 |
|------|-------------------|---------|
| DISC 原始（简短结论式） | 缺推理链 + 可能有条文编号 | P1 + P2 |
| zixun 原始（公式化推理） | 标签词 + 套话收尾 + 绝对化措辞 | P2 + P5 + P6 |

天然 rejected 的核心价值：约 20% 的 rejected 来自真实错误而非程序注入，证明偏好对不是在防正则，而是在教模型区分"好的法律咨询"和"真实场景中常见的坏回答"。天然原始回答中的多重错误问题（如 zixun 同时含标签词+套话+绝对化）不作为混合信号处理——同一条 rejected 在多个痛点维度上都构成负样本，模型在对比学习中自然学会避免所有这些特征。

#### 4.2.3 验收红线

每条 rejected 必须：
- 仍过篇幅检查（100-600 字，不是乱码或空输出）
- `rejected != chosen`（程序注入的 rejected 改动目标字段后，其余内容与 chosen 一致）
- 程序注入的 rejected：改动目标字段后，其余内容与 chosen 保持一致，只改一个痛点
- 任一不满足 → 该痛点扰动失败、报警并丢弃该对

### 4.3 DPO 偏好对配比

总目标 ~1,500-2,200 对（spec 2.4.6），向最难纠的痛点倾斜：

| 来源 | 目标痛点 | 偏好对数量 |
|------|---------|:--:|
| 程序注入 | P3 法律依据幻觉 | ~600-800 |
| 程序注入 | P5 建议空泛 | ~200-300 |
| 程序注入 | P6 过度确定性 | ~300-400 |
| 程序注入 | P2 格式不规范 | ~200-300 |
| 天然 DISC | P1 推理链缺失 | ~150-200 |
| 天然 zixun | P2+P5+P6 混合 | ~150-300 |
| **合计** | | **~1,500-2,200** |

## 5. 三级质量校验

### Level 1：raw 校验（逐条自动）

| 检查项 | 检测方式 | 不合格处理 |
|--------|---------|-----------|
| 篇幅 150-500 字 | 字符数统计 | <150 → 重写（推理链不完整）；>500 → 统计超长比例，人工核实后决定批量压缩或重写 |
| 不含条文编号 | 正则：`第[零一二三四五六七八九十百千\d]+条` | 正则删除编号 → 重检；无法删除的剔除 |
| 不含框架标签词 | 检测"首先/其次/最后"连续使用 ≥ 2 个 | 正则删除标签词 → 检查段落连贯性 → 断裂时调 LLM 局部修 |
| 不含绝对化措辞 | 正则：<code>[一肯必绝]定[能会要]?&#124;毫无[疑异]问&#124;必然</code> | 替换为条件化表述 → 无法替换的标为 P6 问题 |
| 法律名称不虚构 | 提取《XX法/条例》实体，分三类：(a) 现行有效→通过；(b) 已废止但曾存在→放行标记；(c) 从未存在→剔除 | (c) 类替换为"根据相关法律规定" |
| 不编造案情细节 | NER 提取人名/金额/时间/地点，与 question 交叉比对 | 多出的事实要素标为"疑似事实幻觉"，人工抽检确认后剔除 |
| PPL 异常检测（补充） | Qwen2.5-0.5B 本地计算每条 answer 的困惑度，标记 PPL 超过全量均值 3σ 的样本 | 自动标记不自动删除；人工抽检异常样本（预期 < 2%），抓中段截断、主题漂移、重复循环等现有检查漏掉的隐性问题 |
| ⚠ 已知盲区 | NER 能抓实体类编造（人名/金额/时间/地点），但**抓不到叙事性事实补充**（如用户只说"交通事故骨折"，模型续写"术后脸部肿胀、无法进食"）。这类幻觉依赖 prompt 约束 + 生成后抽检，无自动化方案 | 诚实标注边界：Level 1 不承诺 100% 召回案情幻觉 |
| 卡 3/4 专属：法律结论一致性 | 提取重写后 answer 中的法律名称，与原始 answer 中的法律名称比对（LLM 交叉检查） | 不一致 → 回退到原始回答，人工决定 |
| 卡 5 专属：措辞多样性 | 100 条拒答的嵌入聚类或 n-gram 去重 | 相似度过高（>0.9）的拒答对标记，手工改写 |

> **📖 什么是困惑度（Perplexity），为什么这样用**
>
> 困惑度（Perplexity, PPL）衡量模型对一段文本的"意外程度"。通俗理解：一个语言模型逐 token 读完一段文本，每个位置它都会对下一个 token 给出一个预测概率。如果模型一路上都觉得"下一个词很意外"（概率低），PPL 就高；如果模型觉得"这不出所料"（概率高），PPL 就低。
>
> 形式化：$\text{PPL} = \exp\left(-\frac{1}{N}\sum_{i=1}^{N} \log P(w_i \mid w_{<i})\right)$，即所有 token 的对数概率的几何平均的倒数。PPL 越低 = 模型认为这段文本越"自然"。
>
> **PPL 异常 vs PPL 质量排序**：PPL 能做异常检测（找 outlier），但不能做质量排序（挑"更好"的样本）。一条在法律上完全正确但引了一个不常见法律名称的回答，PPL 可能高于一条通顺但法律结论错误的回答——因为 base 模型对冷门术语更"意外"，但这种意外不是质量问题。因此 PPL 只看两端的极端值（> 3σ），不用于对合规样本的排序。异常成因可能是：(a) 中段截断——回答在句中被切断，(b) 主题漂移——前后段落在分析不同的问题，(c) 重复循环——同一句式机械重复。这三类问题正则和质量门无法可靠检测，而 PPL 可以低成本标记。
>
> **为什么用 0.5B 算 PPL**：7,600 条 × 0.5B CPU 推理 ≈ 2-4 小时，用已有环境零额外成本。0.5B 的语言建模能力足以区分"正常语流"和"断裂/漂移/循环"——不需要法律知识，只需要语言流畅度判断。

### Level 2：SFT 渲染校验

- `instruction` 固定为 canonical prompt（不允许变异）
- `input` = raw 的 `question` 原文（不允许修改）
- `output` 非空且过 Level 1 全部检查
- JSON 合法、编码正确

### Level 3：DPO 扰动校验

- `chosen` = raw 的 `answer`（与 SFT output 完全一致）
- `rejected` 非空、过篇幅检查、不是乱码
- `chosen != rejected`
- `instruction` + `input` 与对应的 SFT 样本完全一致

### 7.4 数据消融实验

**问题**：~7,600 条是否是最优规模？数据量翻倍带来的评测指标提升是否显著？这是 spec 2.4.2 提出的数据消融实验——分别用 ~3,800 / ~7,600 条训练，比较评测指标的饱和曲线。

此实验完全在阶段四 SFT 训练时执行——从已冻结的全量数据中抽样 50% 训一轮、100% 训一轮，对比评测指标。阶段三只负责产出全量冻结数据，不参与消融实验。

## 9. 小样冒烟（本次交付）

### 9.1 范围

每卡生成 **10 条** raw（合计 40 条），走通全链路：生成 → raw 校验 → SFT 渲染 → DPO 扰动 → 切分 → 注册。管线验收通过后，~7,600 全量一键执行。

10 条足够将 30% 违规率下的漏检概率降到 3%，同时覆盖大部分法律类别——冒烟的职责是抓系统性崩坏（prompt 完全跑偏、格式全面崩坏），不是精确估算违规率。

### 9.2 冒烟覆盖要求

| Prompt | 覆盖卡 | 冒烟条数 | 额外要求 |
|--------|:--:|:--:|------|
| Prompt A | 卡 1+2 | 10 | 必须包含至少 2 条信息充足 + 2 条信息不足；覆盖 ≥ 8 个不同法律类别 |
| Prompt B | 卡 3 | 10 | 覆盖 ≥ 8 个不同法律类别（DISC 2,696 条分布广，选择多） |
| Prompt C | 卡 4 | 10 | zixun 仅 348 条且集中于婚姻家庭/合同/劳动，覆盖实际拥有的类别即可 |
| Prompt D | 卡 5 | 10 | 覆盖全部 4 种拒答场景，每种至少 2 条 |
| 人工 QA | — | 8 | 从 40 条中每个 Prompt 随机抽 2 条肉眼通读 |

### 9.3 冒烟审核 Checklist

每条冒烟样本逐项检查：

| # | 检查项 | 检测方式 | 硬伤/软伤 |
|---|--------|---------|:--:|
| 1 | 篇幅 150-500 字 | 自动 | 硬伤 |
| 2 | 无条文编号（"第X条"） | 自动 | 硬伤 |
| 3 | 无框架标签词（"首先/其次/最后"连续 ≥ 2） | 自动 | 硬伤 |
| 4 | 无绝对化措辞（"一定/肯定/必然"） | 自动 | 软伤 |
| 5 | 无编造法律名称 | 自动（白名单） | 硬伤 |
| 6 | 推理链四段完整（理解→定性→说理→建议） | 肉眼 | 软伤 |
| 7 | 卡 3/4 专属：法律名称与原始回答一致 | 自动 + 肉眼 | 硬伤 |
| 8 | 卡 5 专属：拒答措辞不雷同 | 肉眼 | 软伤 |

**硬伤**：必须修复（修改 prompt 或调整参数）后重跑冒烟。**软伤**：记录但可接受，在全量时重点关注。

### 9.4 通过标准

- **单卡通过**：10 条中 ≤ 1 条有硬伤，且 0 条有 ≥ 2 个硬伤
- **全局通过**：五张卡全部通过，且 40 条合计硬伤 ≤ 4 个
- **不通过处理**：该卡 prompt 修改 → 重跑该卡 10 条冒烟 → 重新审核
- 最多重跑 2 轮。2 轮后仍有硬伤 → 升级为设计问题，回到 spec 讨论

### 9.5 全量生成中的滚动质量检查

冒烟通过后全量生成时，在生成脚本中内嵌滚动质量检查：每累计生成 50 条，对已完成的样本自动跑 Level 1 正则检查（秒级，不额外调 API），实时打印违规统计。各类违规率达到以下阈值时触发**警告**（不硬停止，由用户判断是否继续）：

| 违规类型 | 警告阈值 |
|---------|:--:|
| 条文编号产出率 | > 10% |
| 框架标签词率 | > 15% |
| 绝对化措辞率 | > 20% |
| 法律名称编造率 | > 5% |

阈值不设硬停止——不同卡的自然违规率不同（如卡 3 DISC 重写的条文编号率可能高于卡 1）。用户看到警告后判断：是 prompt 需要修 → 停止并修正后续生成；是预期内的 → 继续。第一个 50 条完成后（约 1 分钟），就能判断 prompt 有没有系统性问题。
